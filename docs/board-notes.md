# STM32H7S78-DK 開發筆記

這份記錄的是**做這塊板子時實際踩到的坑**，以及花時間才查出來的正確做法。
之後在這塊板子上做別的專案，先讀這份可以省下大量除錯時間。

每一條都標註了「症狀 → 原因 → 解法」，因為症狀往往跟原因看起來毫無關聯。

---

## 板子基本規格

| 項目 | 規格 |
|---|---|
| MCU | STM32H7S7L8H6H，Cortex-M7 @ 600 MHz |
| **內部 Flash** | **只有 64 KB** ← 這點決定了整個架構 |
| 外部 Flash | 128 MB Octo-SPI NOR（Macronix MX66UW1G45G），映射在 `0x70000000` |
| 外部 RAM | 32 MB PSRAM（AP Memory APS256XX），映射在 `0x90000000` |
| LCD | 5 吋 800×480 RGB565，RK050HR18 面板（MB1860 子板） |
| 觸控 | GT911 電容式五點觸控，I2C1，位址 `0xBA` |
| 除錯器 | 板載 ST-Link V3（`VID_0483 / PID_3754`） |

**內部 Flash 只有 64 KB** 是這塊板子最特別的地方。一個 800×480 RGB565 的
framebuffer 就要 750 KB，程式碼根本放不進內部 Flash。所以必須用 XIP 架構：
內部 Flash 放 bootloader，程式本體燒進外部 Flash 直接執行。

## 一、專案建置

### 1.1 必須用 Template_XIP 當基底

ST 韌體包裡 `Projects/STM32H7S78-DK/Templates/Template_XIP` 已經處理好
bootloader、XIP 鏈結腳本、XSPI 記憶體映射。不要從零開始搭。

### 1.2 專案目錄不能隨便搬

**症狀**：編譯報 `No rule to make target 'C:/Middlewares/ST/...'`

**原因**：`.cproject` 用相對路徑 `../../../../../../..` 指向韌體包的
`Drivers/` 和 `Middlewares/`。把專案複製到別的地方，往上爬的層數就錯了，
會爬到磁碟根目錄。

**解法**：專案必須放在 `cube/Projects/STM32H7S78-DK/Templates/<你的專案>`
這個層級。

### 1.3 submodule 一定要抓

**症狀**：缺 `stm32_boot_xip.c`、`stm32h7rsxx_hal_ltdc.c` 等檔案

**原因**：`STM32CubeH7RS` 倉庫把 HAL、CMSIS、BSP、GT911 都做成 submodule，
`git clone --depth 1` 不會帶下來。

**解法**：
```bash
git submodule update --init --depth 1 --recursive
```

### 1.4 元件設定檔要自己補

Template_XIP 不含 `gt911_conf.h`、`mx66uw1g45g_conf.h`、`aps256xx_conf.h`，
但 BSP 需要它們。從 `Projects/STM32H7S78-DK/Examples/BSP/Inc/` 複製過來。

### 1.5 HAL 模組預設全是關的

`stm32h7rsxx_hal_conf.h` 裡 LTDC / I2C / DMA2D / XSPI / LPTIM 預設都被註解掉。
少開一個就是一串 `unknown type name` 錯誤。

LCD 背光用 LPTIM，所以連 LPTIM 都要開——這個很容易漏。

### 1.6 命令列編譯

CubeIDE 可以不開 GUI 編譯，但有兩個雷：

```bash
# 路徑必須用 Windows 反斜線格式，否則 Eclipse 會把 C: 當成 URI scheme
# 報錯 "No file system is defined for scheme: C"
stm32cubeidec.exe -nosplash \
  -application org.eclipse.cdt.managedbuilder.core.headlessbuild \
  -data 'C:\path\to\ws' -import 'C:\path\to\project' \
  -build 'ProjectName/Debug'
```

`-import` 和 `-build` 要在**同一次呼叫**裡，分兩次執行工作區狀態不會保留。

### 1.7 燒錄

```bash
# Bootloader 進內部 Flash（只需第一次）
STM32_Programmer_CLI -c port=SWD mode=UR -w Binary/Boot_XIP.hex -v

# 應用程式進外部 Flash，必須指定 external loader
STM32_Programmer_CLI -c port=SWD mode=UR \
  -el ".../ExternalLoader/MX66UW1G45G_STM32H7S78-DK.stldr" \
  -w Appli/Debug/App.elf -v
```

漏掉 `-el` 就燒不進外部 Flash。

**硬體前提**：BOOT0 滑動開關要在 SW1 位置。Option Bytes 需要
`XSPI1_HSLV=1`、`XSPI2_HSLV=1`、`VDDIO_HSLV=0`（出廠通常已正確，可用
`-ob displ` 確認）。

## 二、顯示（LTDC）── 這裡的坑最多

### 2.1 BSP_LCD_Init 預設是 ARGB8888，不是 RGB565

**症狀**：畫面左右重複兩次、下半部是彩色雜訊、顏色完全不對

**原因**：`BSP_LCD_Init()` 內部呼叫
`BSP_LCD_InitEx(..., LCD_PIXEL_FORMAT_RGB888, ...)`，而 BSP 把 RGB888 實作成
**ARGB8888（4 bytes/pixel）**。如果你的繪圖是 RGB565（2 bytes/pixel），
硬體讀取的行距就是你的兩倍，畫面自然錯亂。

**解法**：明確指定像素格式。
```c
BSP_LCD_InitEx(0, LCD_ORIENTATION_LANDSCAPE,
               LCD_PIXEL_FORMAT_RGB565, 800, 480);
```

### 2.2 換 framebuffer 千萬不要用 BSP_LCD_SetLayerAddress

**症狀**：畫面持續閃爍、出現橫向黑線

**原因**：`BSP_LCD_SetLayerAddress()` → `HAL_LTDC_SetAddress()` →
`LTDC_SetConfig()`，而 `LTDC_SetConfig` 為了換一個位址，**重寫整組圖層暫存器**：
視窗座標、像素格式、混色係數、行長、行數……而且好幾個是這種寫法：

```c
LTDC_LAYER(...)->CFBLR &= ~(mask);   /* 先清成 0 */
LTDC_LAYER(...)->CFBLR  = (value);   /* 再寫回 */
```

兩步之間暫存器是 0。面板持續掃描，掃到那一瞬間就是黑線。

**解法**：只寫 `CFBAR` 一個暫存器。它是 shadow register，寫入不會立即生效，
等垂直消隱重載時整批原子切換。

```c
LTDC_Layer1->CFBAR = new_framebuffer_addr;   /* 單次寫入，無中間狀態 */
LTDC->SRCR = LTDC_SRCR_VBR;                  /* 垂直消隱時生效 */
while (LTDC->SRCR & LTDC_SRCR_VBR) { }       /* 等它真的切過去 */
```

**這是本專案最重要的一條**，任何用 LTDC 做雙緩衝的專案都適用。

初始化時記得先讓 BSP 進入 no-reload 模式，否則 `SetLayerAddress` 仍會走
立即重載那條路：
```c
BSP_LCD_Reload(0, BSP_LCD_RELOAD_NONE);
```

### 2.3 雙緩衝的索引很容易寫反

**症狀**：畫面閃爍，但暫停（畫面靜止）時不閃

**原因**：交換後把繪圖目標指到「正在顯示」的那塊緩衝區，等於雙緩衝失效，
每格都在使用者眼前重畫。

**判斷技巧**：如果**畫面靜止時不閃、有動畫時才閃**，幾乎可以確定是這個問題，
而不是時序或硬體問題。

**解法**：用紙筆或小程式把狀態機跑幾格，確認「顯示的」和「繪製的」永遠相反。

### 2.4 PSRAM 要設成 write-through

Framebuffer 放在 PSRAM，CPU 寫入會停在 D-Cache，而 LTDC 是直接從 PSRAM 讀，
兩邊看到的內容會不一致。

```c
MPU_Region_InitTypeDef mpu = {0};
mpu.BaseAddress  = 0x90000000;
mpu.Size         = MPU_REGION_SIZE_4MB;
mpu.IsCacheable  = MPU_ACCESS_CACHEABLE;
mpu.IsBufferable = MPU_ACCESS_NOT_BUFFERABLE;   /* 這組合 = write-through */
mpu.TypeExtField = MPU_TEX_LEVEL0;
```

註：實測這項對**速度**沒有明顯影響，但對**正確性**是必要的。

### 2.5 PSRAM 開機是隨機內容

一定要在顯示開啟前把兩塊 framebuffer 清空，否則第一幀會看到雜訊。

### 2.6 直立顯示要自己做旋轉

BSP 只支援 `LCD_ORIENTATION_LANDSCAPE`，沒有 portrait 選項。
要做直立畫面就得在繪圖層自己轉座標：

```c
/* 邏輯直立 (x,y) -> 實體橫向 (y, GFX_W-1-x) */
offset = (GFX_W - 1 - x) * PHYS_W + y;
```

觸控讀進來要做**反向**轉換，兩者必須互為逆運算，否則手指按的位置和畫面上
按鍵的位置對不上。這點務必寫測試驗證。

## 三、DMA2D ── 已解決

### 3.1 根本原因：CPU 讀取時的快取一致性

**症狀**：畫面出現大範圍白色雜點（偶發、一整片同時出現），控制區出現遊戲
場地的顏色碎片。

**原因**：DMA2D 繞過 CPU 直接寫 PSRAM，但 **CPU 讀取時仍會從 D-Cache 取值**，
拿到的是 DMA2D 寫入之前的舊內容。

這裡最容易誤判：framebuffer 已經設成 **write-through**，所以我一開始排除了
快取的可能。但 write-through 只保證「CPU 的**寫入**」會穿透到 PSRAM，
**完全管不到「CPU 的讀取」這個方向**。DMA 寫、CPU 讀，仍然需要手動失效快取。

**解法**：讀取被 DMA2D 寫過的區域之前，先失效該範圍的快取。

```c
SCB_InvalidateDCache_by_Addr((uint32_t *)addr, (int32_t)byte_len);
```

### 3.2 診斷方法（值得複製到其他專案）

雜點是偶發的，在遊戲裡很難定位。做法是把 DMA2D 單獨拉出來寫成診斷程式
（`app_src/dma2d_probe.c`），用固定樣式反覆填色再逐一驗證，把「偶發」變成
「可量測的錯誤率」，並在出錯當下記錄硬體暫存器狀態。

四個階段，逐步加壓：
1. 單次大面積填色 ×200
2. 200 格小矩形 ×100 回合（模擬遊戲用法）
3. DMA2D 與 CPU 交錯寫入相鄰區域 ×200
4. 連續發送不逐次等待 ×100

結果寫進全域變數，用 SWD 讀出來，不需要 UART：
```bash
addr=$(arm-none-eabi-nm app.elf | grep " probe_errors$" | awk '{print "0x"$1}')
STM32_Programmer_CLI -c port=SWD mode=HOTPLUG -r32 $addr 1
```

**關鍵線索**：錯誤像素的實際值是「上一回合的顏色」而不是隨機值 → 說明不是
寫錯資料，是**讀到了舊內容**。同時硬體狀態顯示 TC 已置位、START=0、傳輸次數
完全正確 → 傳輸本身沒問題。兩者一對照，就只剩快取這一個可能。

### 3.3 其他必須做對的事

**不要用 HAL_DMA2D_Start + HAL_DMA2D_PollForTransfer**：
`PollForTransfer` 的等待迴圈包在 `if (CR & DMA2D_CR_START)` 裡。小矩形傳輸
很快，常在程式走到 poll 之前就結束，START 已被硬體清 0，整個等待被跳過。
而 `HAL_DMA2D_Start` 又從不清除 TC 旗標，殘留的 TC=1 會讓下一次等待立刻返回。

直接操作暫存器比較可靠（見 `app_src/dma2d.c`）：
```c
DMA2D->OCOLR = color;        /* R2M + RGB565 輸出時直接放 16 位元值 */
DMA2D->OMAR  = dest_addr;
DMA2D->OOR   = stride - width;
DMA2D->NLR   = (width << DMA2D_NLR_PL_Pos) | height;
DMA2D->IFCR  = DMA2D_IFCR_CTCIF | DMA2D_IFCR_CTEIF | DMA2D_IFCR_CCEIF;
DMA2D->CR   |= DMA2D_CR_START;

while (DMA2D->CR & DMA2D_CR_START) { }   /* 看 START 位，不要看旗標 */
__DSB();
```

**注意 OCOLR 的格式取決於你怎麼呼叫**：
- 直接寫暫存器：依輸出格式，RGB565 就放 16 位元值
- 走 `HAL_DMA2D_Start`：**一律要 ARGB8888**，HAL 自己narrow。傳 RGB565
  進去會讓紅色通道整個變 0，畫面發灰

**小矩形用 CPU 反而快**：DMA2D 每次要設四個暫存器再啟動，幾百個像素的矩形
設定成本大於傳輸本身。實測門檻約在 1024 像素。

### 3.4 混用硬體與 CPU 繪圖時必須同步

**症狀**：某個區域的小圖案不完整而且會閃，但其他區域正常。

**原因**：填色是非同步的（發出傳輸後函式就返回）。若隨後用 CPU 在同一區域
畫小東西，DMA2D 正在進行的傳輸會把剛畫好的內容蓋掉。

這個 bug 只在**同一塊區域混用兩種路徑**時出現。俄羅斯方塊的預覽框正是這樣：
框底 190x68 走硬體，裡面的方塊 14x14 走 CPU，於是方塊被框底抹掉。

**解法**：在繪圖層設一個同步點，任何 CPU 寫入 framebuffer 之前先等硬體停下來。

```c
/* gfx.c */
static gfx_sync_hw_fn g_sync_hw;
static inline void sync_hw(void) { if (g_sync_hw) g_sync_hw(); }

/* 韌體初始化時 */
gfx_set_fill_hw(dma2d_fill);
gfx_set_sync_hw(dma2d_wait);
```

**同步點的粒度很重要**：放在 `gfx_pixel` 會讓畫一行字多做上千次檢查。
應該放在 `gfx_char`、`gfx_circle` 這種「一次寫幾百個像素」的函式開頭。

之後改用 GPU2D 也是同一個模式，這個 callback 機制可以直接沿用。

### 3.5 效能

| | 繪製 | 等待垂直消隱 | fps |
|---|---|---|---|
| 純 CPU | 9.87 ms | 5.71 ms | 64 |
| DMA2D（門檻 1024px） | 8.94 ms | 6.63 ms | 64 |

幀率相同，因為瓶頸是面板的 60 Hz。DMA2D 的價值在於**騰出 CPU 時間**，
以及未來做全畫面重繪（賽車類）時才會顯現。

### 3.6 這顆還有更強的 GPU2D

`GPU2D_BASE` 存在，HAL 有 `stm32h7rsxx_hal_gpu2d.c`。那是 NeoChrom GPU，
支援旋轉、縮放、紋理貼圖、抗鋸齒——DMA2D 只能做矩形搬運與混色。
做賽車這類需要旋轉縮放的遊戲時應該用它。

## 四、效能實測數據

用 DWT cycle counter 在板子上實際量測（600 MHz）：

| 項目 | CPU 繪圖 | DMA2D（門檻 1024px） |
|---|---|---|
| 每格繪製 | 9.87 ms | 8.94 ms |
| 等待垂直消隱 | 5.71 ms | 6.63 ms |
| 合計 | 15.58 ms | 15.57 ms |
| 幀率 | 64 fps | 64 fps |

**結論**：兩者幀率相同，因為瓶頸是面板的 60 Hz 更新率，不是繪製速度。
單純的 2D 遊戲用 CPU 畫就夠了；DMA2D 的價值要在全畫面重繪時才顯現。

註：目前遊戲的方塊是 24×24 = 576 像素，低於 1024 的門檻，所以場地其實
還是走 CPU。若把門檻調低反而更慢（設定成本大於傳輸）。真正要發揮 DMA2D，
應該改成「一次傳輸畫一大塊」而不是「每個小方塊一次」。

量測方法：
```c
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
uint32_t t0 = DWT->CYCCNT;
/* ... 要量的程式 ... */
uint32_t cycles = DWT->CYCCNT - t0;
```

之後用 `STM32_Programmer_CLI -c port=SWD mode=HOTPLUG -r32 <變數位址> 1`
就能把數值讀出來，不需要接 UART。變數位址用
`arm-none-eabi-nm app.elf | grep 變數名` 查。

## 六、中文字型

BSP 內建字型只有 ASCII。中文要自己做點陣字：

`tools/genfont.py` 用 Pillow 從微軟正黑體算出點陣圖，產生 C 陣列。
24×24 每字 72 bytes，74 個字只要 5.2 KB。

搭配 `tools/checkglyphs.py` 在建置前檢查所有 UI 字串用到的字都在字型表裡——
**漏字在畫面上是「什麼都不顯示」，不會報錯**，所以這個檢查很有必要。

## 七、測試策略

沒有板子也能測大部分東西：用 **QEMU 的 `mps2-an500`**（Cortex-M7，跟這塊板子
同核心），配合 semihosting 輸出。

```bash
qemu-system-arm -M mps2-an500 -nographic \
  -semihosting-config enable=on,target=native -kernel test.elf
```

需要 `-specs=rdimon.specs`，並在啟動碼裡呼叫 `initialise_monitor_handles()`
（用 `-nostartfiles` 時 crt0 不會自動呼叫它，輸出會是空的）。

可以測到的：遊戲邏輯、座標旋轉、字型資料、記憶體越界、觸控映射。
測不到的：真實顏色、畫面方向、觸控準度、閃爍。這些只能燒上板用眼睛看。

**教訓**：純數學測試驗證了「旋轉映射是雙射」，卻沒發現**畫面整個上下顛倒**——
雙射只保證一對一，不保證方向正確。所以務必把畫面**渲染成 PNG 檢查**
（`test/render_shot.c` + `tools/raw2png.py`），視覺問題只有看才看得出來。

## 八、通用教訓

1. **症狀的位置就是線索**。「只有 A 鈕那側閃」讓我算出是 6 px 的重繪縫隙；
   「暫停時不閃」直接證明問題在動畫而非硬體時序。使用者的精確描述比我的推理有用。

2. **二分法比推理快**。花了三輪猜 DMA2D 的問題出在哪，最後直接把它關掉，
   一次就確定了範圍。

3. **量測，不要假設**。我先後假設「繪製太慢」「快取沒寫回」，實測後都被推翻。
   DWT cycle counter 花五分鐘裝上去，省下數小時瞎猜。

4. **測試要先驗證它會失敗**。寫完閃爍偵測測試後，我故意把 bug 改回去確認測試
   真的會 FAIL——第一版測試其實是無效的，改回去也照樣 PASS。

## 九、SWD 除錯的連線模式（另一個專案踩過的坑）

### 9.1 mode=UR 會讓核心永遠停在 reset vector

**症狀**：讀 RAM marker 永遠是 0，看起來像「main() 根本沒跑」「iRoT 擋住 boot」。

**原因**：`mode=UR`（Connect Under Reset）每次連線都 halt-on-reset。
而 CLI 的每個指令是**獨立連線** —— 你 `-g` run 之後，下一個讀取指令重新連線
又把核心 halt 回 reset 點，marker 永遠沒機會被寫。

```bash
# ❌ 跨連線讀取，每次都把核心 halt 掉
STM32_Programmer_CLI -c port=SWD mode=UR -r32 0x24000100 1

# ✅ HOTPLUG 不 halt 執行中的核心
STM32_Programmer_CLI -c port=SWD mode=HOTPLUG -r32 0x24000100 1

# ✅ 或單一連線內做完所有動作
STM32_Programmer_CLI -c port=SWD mode=0 -hardRst -r32 0x24000100 4
```

**燒錄用 UR、觀察執行狀態用 HOTPLUG**，不要混用。

> 這個坑讓另一個專案誤判成「iRoT secure boot 擋住未簽名映像」，
> 花了整整一個 session 追不存在的問題。實際上 chainload 一直是通的。

### 9.2 ST-Link VCP 是 UART4，不是 USART2

從 Nucleo 等其他板子抄來的 `USART2 / PA2-PA3` 在這塊板子行不通。

| | 值 |
|---|---|
| UART | **UART4** |
| TX / RX | **PD1 / PD0** |
| AF | **8** |
| Baud | 115200 8N1 |

Boot 跟 Appli **兩個 context** 都要設（hal_conf 啟用模組、hal_msp 加 MspInit、
main.c 加 huart4 + `__io_putchar`）。

### 9.3 GPIO 在 AHB4：0x58020000

H7RS 系列跟傳統 H7 不同。

```c
#define GPIOD_BASE_ADDR 0x48020C00   // ❌ 無效映射 → BusFault → LOCKUP
#define GPIOD_BASE_ADDR 0x58020C00   // ✅ AHB4PERIPH_BASE + 0x0C00
```

症狀是 CFSR=0x8200、HFSR LOCKUP。寫 raw 暫存器（不透過 HAL）時特別容易踩。

### 9.4 reset 直後的時鐘是 HSI 16MHz

還沒跑 `SystemClock_Config()` 之前是 **HSI 16MHz**，不是 64MHz。
早期 raw UART print 的 BRR 要照 16MHz 算，否則會變成約 461k baud，終端機讀不到。

### 9.5 AFR 的位元組位置

```c
/* pin N 的 AF 欄位在 AFR[N/8] 的 bits[(N%8)*4 +: 4] */
GPIOD->AFR[0] = (8 << 4);    /* PD1 = AF8 */
```

寫錯位移會設到別的 pin，症狀是「UART 初始化了但沒輸出」。

## 十、同一份韌體換一塊板子就閃 ── PSRAM 時脈邊際

### 10.1 症狀

畫面上有很多細線在閃，**暫停讓畫面完全靜止也照閃**。
同一顆 bin 在原本那塊板子上完全正常。

第二節列的五個閃爍成因（`SetLayerAddress`、雙緩衝索引寫反、write-through、
DMA2D 快取、硬體/CPU 混用）在這個情況下全都不適用——那些都是程式問題，
程式沒變卻換板子就發作，就要往硬體時序想。

### 10.2 根因

framebuffer 在外部 PSRAM，BSP 把 XSPI1 設在這顆晶片的規格上限 **200 MHz**
（`stm32h7s78_discovery_xspi.c` 的 `BSP_XSPI_RAM_Init`，`xspi_max_freq`）。
時序餘裕會隨 PCB 走線、晶片批次、溫度、供電而變，**不同板子可能一塊在邊界的
安全側、一塊在錯誤側**。落在錯誤側時讀取會偶發單一位元取樣錯誤。

關鍵是「誰在讀」：

| | 受影響程度 |
|---|---|
| CPU 讀 framebuffer | 幾乎不受影響——走 D-Cache，而且遊戲很少讀回畫面 |
| **LTDC** | **每秒 60 次、每個像素都直接從 PSRAM 讀** |

每個讀錯的位元就是螢幕上一個變色像素。錯誤是隨機的，所以**每一幀壞掉的位置
都不同**，那些像素就以刷新率在閃。LTDC 沿掃描線 burst 讀取，錯誤會沿同一列
聚集，看起來就是「很多線條在閃」而不是散開的雜點。

### 10.3 解法：把 XSPI1 時脈減半

`MX_XSPI_RAM_Init()` 是 `__weak`，在應用層定義同名函式就能覆寫，
**不必改韌體包裡的任何檔案**（重跑 `setup.sh` 也不會被蓋掉）。

複製 BSP 版本的內容，只改兩處：

```c
/* 分頻 = prescaler + 1，所以這樣寫等於時脈減半：200MHz -> 100MHz */
hxspi->Init.ClockPrescaler = (Init->ClockPrescaler + 1U) * 2U - 1U;

/* refresh 是「2us 換算成幾個時脈」，時脈變了一定要跟著重算，
   否則會違反 PSRAM 的 tCEM 上限，反而更糟 */
hxspi->Init.Refresh =
    ((2U * (hspi_clk / (hxspi->Init.ClockPrescaler + 1U)) / 1000000U) - 4U);
```

只影響 PSRAM（XSPI1）。程式碼在外部 NOR Flash 上（XSPI2），不受影響。

**沒有效能代價**：LTDC 只需要約 46 MB/s（800×480×2 bytes × 60 Hz），
100 MHz 的 PSRAM 頻寬遠遠夠用。實測 fps 沒有下降。

因為這是**板子個體差異**，不是所有板子都需要，所以沒有預設打開。
畫面會閃再加上這段。

### 10.3.1 調取樣點沒有用，只有降頻有用

XSPI 有兩個移動取樣點的旋鈕，直覺上會想先試這個而不是降頻。實測四種組合：

| 設定 | 錯誤字數 | 乾淨區塊 |
|---|---|---|
| 200MHz 取樣 NONE、DHQC 關（BSP 預設）| 1,466,194 | 15/256 |
| 200MHz 取樣半週期、DHQC 關 | 1,357,359 | 19/256 |
| 200MHz 取樣 NONE、DHQC 開 | 1,386,924 | 13/256 |
| 200MHz 取樣半週期、DHQC 開 | 1,414,165 | 4/256 |
| **100MHz 取樣 NONE、DHQC 關** | **0** | **256/256** |

四種組合在 200MHz 全都是一百多萬個錯誤，彼此的差異只是雜訊。
**移動取樣點有明顯改善才代表是相位問題**；這裡沒有，所以是整個資料視窗在
200MHz 下就不夠，屬於訊號品質而不是相位。

另外，prescaler 是整數分頻，核心時脈 200MHz 之下只有 /1=200、/2=100、
/3=66.7 這幾檔，**沒有 150MHz 這個選項**。降到 100MHz 不是保守過頭，
那就是次一檔。

### 10.4 診斷方法（這裡踩了很多坑，值得記下來）

目標是量出「PSRAM 讀回來的資料對不對」，但這件事比想像中難測，
以下每一個都實際誤導過我：

**❌ 用偵錯器讀寫 PSRAM 驗證**
`STM32_Programmer_CLI` 的存取會跟正在全速掃描的 LTDC 搶匯流排，
測到的錯誤可能是競爭而不是記憶體。而且結果不一致——同樣的區域重測三次，
錯誤位址每次都不同，換一塊區域又變成零錯誤。**必須讓韌體自己測。**

**❌ 寫完直接讀回來比對**
framebuffer 區是 write-through，CPU 的**寫入**會穿透到 PSRAM，
但**讀取**仍然可能從 D-Cache 拿到剛剛寫進去的值，等於什麼都沒測到。

**❌ 補一個 `SCB_InvalidateDCache_by_Addr()` 就好**
對 write-through 區域可以，對 **write-back 區域會把還沒寫回去的資料直接丟掉**。
我拿內部 SRAM 當對照組時就是這樣——錯誤率 100%，每個字都錯。

**✅ 測試區設成 non-cacheable，並且一定要有對照組**

```c
mpu.Number       = MPU_REGION_NUMBER6;
mpu.BaseAddress  = 0x91000000;          /* framebuffer 之外的 PSRAM */
mpu.Size         = MPU_REGION_SIZE_16MB;
mpu.IsCacheable  = MPU_ACCESS_NOT_CACHEABLE;
mpu.IsBufferable = MPU_ACCESS_NOT_BUFFERABLE;
mpu.TypeExtField = MPU_TEX_LEVEL1;
```

對照組用**內部 SRAM 跑完全相同的檢測程式碼**。內部 SRAM 不可能出錯，
所以只要對照組不是 0，就代表檢測程式本身有問題，PSRAM 那組數字也不能信。
上面那三個坑，全都是靠對照組爆掉才抓出來的。

**逐塊掃描能分辨兩種完全不同的原因**：

| 錯誤分布 | 代表 |
|---|---|
| 集中在特定區塊 | 實體壞格 → 把 framebuffer 挪到乾淨區域可以繞開 |
| **均勻散布在整片** | **時序/設定問題 → 換位址沒用，要降頻** |

實測結果是後者：16MB 分成 256 塊、每塊跑三輪，
**0 個乾淨區塊**，總錯誤 1,369,266 個字。降頻後 **256/256 全乾淨、錯誤 0**。

### 10.5 兩個假線索

**LTDC 的 `ISR` 旗標是黏著的**。直接讀到 `FUIF|TERRIF`（`0x6`）看起來像
FIFO underrun，但那可能只是開機瞬間發生過一次。要每幀讀完就寫 `ICR` 清掉，
用計數對比幀數才有意義。實測清乾淨之後 underrun 一直是 0，
**這條路是死的**——問題不在頻寬。

**`STM32_Programmer_CLI` 燒錄時的 `Data mismatch` 可能是假警報**。
連續三次在同一位址報同樣的錯，看起來像 Flash 壞格，但重新讀回內容跟映像
完全一致。**要另外讀回來比對才算數**，不要直接相信驗證階段的錯誤訊息。

### 10.6 教訓

**畫面問題先確認是程式還是硬體**：暫停讓畫面靜止還在閃、而且同一份 bin
在另一塊板子正常——這兩點就足以把程式邏輯排除掉。

**同一份韌體換板子就出問題，先降頻試試**。外部記憶體介面的時序餘裕是板子
個體差異最容易出事的地方，降頻是最快的驗證手段，一次就能確認方向對不對，
比任何合成測試都快。

## 十一、硬體 JPEG 解碼（album 專案踩的雷，整批都在這）

### 11.1 ChromaSubsampling = 0 是 4:4:4，不是 4:2:0

HAL 的定義：`0=4:4:4、1=4:2:0、2=4:2:2`。把 0 當成 4:2:0 是整個 album
專案最貴的一個誤認 —— 緩衝區照 4:2:0（每像素 1.5 bytes）配，但相機直出的
JPEG 很多是 4:4:4（每像素 3 bytes），需要的空間是兩倍。

| 取樣 | MCU 尺寸 | 每 MCU bytes | 每像素 |
|---|---|---|---|
| 4:4:4 | 8x8 | 192 | 3.0 |
| 4:2:2 | 16x8 | 256 | 2.0 |
| 4:2:0 | 16x16 | 384 | 1.5 |

輸出緩衝區要照 4:4:4 的最壞情況配，容量檢查與長度夾制也要照實際取樣算。

### 11.2 輸出緩衝區不夠時，HAL 會繞回開頭續寫

不會報錯、不會停 —— 就是默默把照片尾端的 MCU 蓋到緩衝區開頭。畫面症狀：
**「照片底部跑到最上面、底部殘留舊資料」**。使用者一說出這句描述，就該
直接朝環繞查，不要繞去查繪圖邏輯（我們繞了四個錯誤假設才回來）。

### 11.3 DataReadyCallback 裡不要呼叫 HAL_JPEG_ConfigOutputBuffer

想在回呼裡「把緩衝區往後推」防覆蓋是個陷阱：HAL 在**解碼結束時也會呼叫
這個回呼**，這時再餵新緩衝區，HAL 就當作還能繼續輸出，反覆觸發直到把
整塊緩衝區吃光。症狀是輸出長度「精確等於緩衝區容量」—— 這種剛好卡在
上限的數字幾乎一定是人為邊界，不是資料本身。

正確做法：一開始就把整塊交給 `HAL_JPEG_Decode()`，回呼只記錄
「這批資料寫到哪裡為止」（用結束位移取最大值，不要累加 —— HAL 對同一批
資料可能回呼兩次）。

### 11.4 HAL_JPEG_Decode 返回後讀不到輸出長度

HAL 結束時先用 DataReadyCallback 把長度交出來，然後把 `JpegOutCount`
清成 0。`__weak` 的預設回呼什麼都不做，長度就掉了 —— 必須自己實作回呼。

### 11.5 解碼器會多寫「MCU 補齊」的部分

高度會補到 MCU 邊界（4:2:0 是 16 的倍數）：1800 高實際寫到 1807 列。
容量檢查照 `寬x高` 算會少算，緩衝區之間也因此**不要首尾相接**，
留一段空白當安全邊界，溢出時不會立刻毀掉隔壁的資料。

### 11.6 jpeg_utils 的 RGB888 是 BGR 順序

`JPEG_RED_OFFSET` 等常數是位元位移不是位元組索引；預設 RED_OFFSET=16，
記憶體順序是 B,G,R。設 `JPEG_SWAP_RB=1` 才是 R,G,B。RGB565 沒這問題
（16 位元值整個寫入），所以從 565 換到 888 時才會突然中招。

### 11.7 縮放的目的地尺寸不要用比例反算

`(H * ((GFX_H<<16)/H)) >> 16` 兩次截斷會讓 800 變 799，最後一列永遠
沒畫到（留著清畫面的黑）。填滿模式的目的地就是整個螢幕，直接寫死，
讓誤差落在來源取樣座標上（那裡差一個像素看不出來）。

## 十二、BSP 的其他不對稱陷阱

### 12.1 BSP_LCD_DisplayOn 不會開背光

`DisplayOff` 順手把背光腳（GPIOG15）從 LPTIM PWM 改成一般輸出並拉低，
`DisplayOn` 卻完全不碰它 —— 關得掉、開不回來。DisplayOn 之後要自己把
GPIOG15 拉高（不用亮度調節的話維持一般輸出即可）。

### 12.2 BSP_SD_IsDetected 只讀不設定偵測腳

真正設定偵測腳的是 `BSP_SD_Init()`。在第一次 Init 之前呼叫 IsDetected，
讀到的是未初始化的浮接腳位 —— 沒插卡會被誤判成有卡。開機要自己先把
`SD_DETECT_PIN` 設成輸入再開始判斷。

### 12.3 觸控要消抖，座標要當下抓

電容觸控在放開瞬間會彈跳：「讀到一次沒碰到」不代表放開了（要連續多次），
「確認有碰到之後再讀座標」會撲空（輕點時手指已離開）。原則：確認的當下
就把座標抓下來；等待放開要連續數次都讀不到才算。

## 十三、建置系統的陷阱

- **產生出來的 makefile 內含絕對路徑**。搬動或改名專案目錄後 make 會
  `No rule to make target`—— 這訊息**不含 error 字樣**，輸出過濾若只抓
  error/warning 會把失敗顯示成成功。把 Debug/ 刪掉重新產生，不要用 sed
  改（`grep -rl` 會把 .o 檔也列進去改壞）。
- **CubeIDE headless 被強制中止後**，workspace 留下 .lock 與未儲存狀態，
  下一次啟動會卡在復原掃描很久。能用 make 就用 make。

## 十四、省電、按鍵與觸控（album 專案第二輪踩的雷）

### 14.1 __WFI() 會讓 SWD 完全失聯

把輪詢迴圈的 `HAL_Delay()`（忙等）換成 `__WFI()` 睡眠很省電，但核心一睡，
除錯介面的時脈就被關掉 —— SWD 直接報
`Unable to read device id from ROM table`，連讀個變數都做不到。

救援方式：`mode=UR`（連線時按住重置，核心來不及睡）仍然連得上，可以重燒。
根治：開機時呼叫 `HAL_DBGMCU_EnableDBGSleepMode()`。代價是省電效果打折，
但開發階段一定要開。

### 14.2 BSP_LCD_SetBrightness(0) 關不掉背光

公式 `Pulse = (PERIOD+1) * Brightness / 100 - 1`，Brightness=0 時
`0 - 1` 在 uint32 下溢成 `0xFFFFFFFF`，PWM 永遠不翻轉。
0% 要另外處理：把背光腳切成一般 GPIO 輸出並拉低。

回到非 0 時記得把腳位還原成 `GPIO_MODE_AF_PP` + `LCD_LPTIMx_CHANNEL_AF`，
否則 SetBrightness 改了比較值也沒用（腳位已經不歸 LPTIM 管）。

### 14.3 亮度要照感知分檔，不是線性

人眼對亮度接近對數感知，`100/75/50/25` 看起來差別很小。
實用的級距是 `100/50/20/6/0`。

### 14.4 「事件不會漏」和「反應快」是兩件事

按鍵從輪詢改成 EXTI 中斷，解決的是「解碼那 1.5 秒按了會漏掉」；但如果
中斷只立旗標、實際動作留給主迴圈，使用者還是要等 1.5 秒才看到反應。

兩個層次都要處理：
- 能在中斷裡完成的就在中斷裡做（亮度只是寫 GPIO 與 LPTIM 暫存器，很快）
- 需要主迴圈的（暫停、換頁）→ 讓長時間工作**可以中途放棄**：
  在管線各階段之間、以及大迴圈裡每隔幾十列檢查一次旗標，
  最壞反應時間從 1.5 秒壓到幾十毫秒

註：中斷裡不要碰 RCC（時脈開關），先在初始化時開好。

### 14.5 旗標的設定與清除必須對稱

「可中斷」等於引入狀態。加了中斷檢查卻沒想清楚「誰負責清」，就會出現：
暫停中每次觸碰都把旗標立起來 → 按繼續離開時旗標還在 → 下一張一開始解碼
就被判定要放棄 → 立刻又彈回暫停 → **永遠出不去**。
把所有出口收斂到一個 `xxx_exit()` 函式裡統一清除。

### 14.6 BSP_TS_EnableIT() 會讓觸控輪詢失效

啟用觸控中斷後，ISR 只清 EXTI 旗標是不夠的 —— GT911 的資料沒被讀走就
不再回報新觸碰，`BSP_TS_GetState()` 之後永遠回傳「沒碰到」，觸控整個死掉。

要正確使用中斷，回呼裡仍得做一次 I2C 把資料讀走，省不到什麼。
如果只是偶爾要判手勢，**維持輪詢就好**。

而且：**軟體重置不會重置 GT911**，晶片會停在中斷模式，症狀跨重燒持續存在，
必須拔電才會回復（跟 SD 卡那個坑同一個道理）。

### 14.7 快速滑動時觸控會漏報

手指快速移動時控制器會掉幾筆座標。若「一讀不到就結束手勢」，位移只算到
中斷點為止 —— 橫向滑動通常比較快，所以特別容易失效，而慢而長的縱向滑動
卻正常。這個方向性差異本身就是線索。

正確做法：容忍約 150ms 的漏報再判定放開，並取**整段過程中的最大位移**
而不是放開瞬間的位置。

## 十五、影像重取樣的畫質（album 專案第三輪）

症狀是「照片邊緣鋸齒太嚴重」。這一章的教訓大多與板子無關，但**方法**值得複製到
任何有畫質問題的專案。

### 15.1 先建 PC 測試台，不要在板子上瞎試

畫質只能用眼睛判斷，而在板子上改一次要重編、重燒、還得手動操作選單才看得到
一張照片，一輪好幾分鐘。`projects/album/test/` 把「解碼之後」的整段管線搬到 PC，
一次跑完幾十種參數組合並排比較。

**關鍵是直接 `#include photo.c` 本體，不要重寫一份演算法。** 重寫一份「應該一樣」
的程式碼來測，測到的就不是板子上實際跑的東西 —— 第七章那個「純數學測試通過、
畫面卻整個上下顛倒」就是這樣來的。

為此把緩衝區位址改成從 `PSRAM_BASE` 算起（`-DPSRAM_BASE=` 可指到 malloc 的記憶體），
把調校常數改成 `#ifndef` 可覆寫。這兩個小改動讓韌體端數值完全不變，卻讓整個
管線變得可在 PC 上參數化測試。

踩過的坑：測試台直接呼叫管線中段，漏了 `photo_init()` 裡的建表，
結果 sRGB 對照表全是 0、反查一律回傳 255、整張變白。
**「輸出全白」「兩個變體位元組完全相同」這種結果要先懷疑旗標沒生效或初始化沒做，
不要急著解讀成演算法的差異。**

### 15.2 整數邊界的盒狀濾波會產生規律階梯

`sy0 = (dy*step)>>16; sy1 = ((dy+1)*step)>>16` 這種寫法，來源像素非全進即全出。
2.25 倍縮放時盒子大小會以 **2,2,2,3 的週期**跳動，取樣中心跟著漂移，邊緣每四個
目的像素就錯開一次 —— 規律的階梯比隨機誤差刺眼得多。而且每個目的像素只由
2~3 顆來源像素平均，灰階過渡只有寥寥幾級，邊緣幾乎是硬跳。

正解是**分數覆蓋率**：邊界上的來源像素按重疊比例加權（`sx1` 改成無條件進位，
權重 = 兩個方向的重疊量相乘）。

### 15.3 重取樣必須在線性光空間做

重取樣的本質是加權平均，而**平均只在線性光空間才有物理意義**。JPEG 解出來是
sRGB（感知編碼，約 gamma 2.2），直接對編碼值平均等於假設亮度尺度是線性的。
誤差集中在高頻，也就是邊緣 —— 正好是鋸齒問題所在。

### 15.4 這兩件事是相乘的，不是相加的

對「線性光 Lanczos」的平均絕對差（越小越好）：

| | sRGB | 線性光 |
|---|---|---|
| 整數盒 | 21.65 | 16.84 |
| 分數覆蓋 | 19.05 | **7.59** |

單獨做任一項只改善 12~22%，兩項一起卻好了 65%。若彼此獨立，預期值是 14.9。

原因：整數盒把邊緣位置量化得太粗，色彩空間的精度根本沒東西可發揮；
幾何修正之後，色彩空間才成為限制因素。**沒有便宜的捷徑，兩個必須一起做。**

這也是一個一般性的陷阱：**逐項比較會低估組合效果**。我一開始只比了
「分數覆蓋 vs 原版」（12%）就下結論說主要貢獻來自線性光，那是比較順序造成的假象。

### 15.5 銳化不能取代好的濾波器

文獻明確反對縮圖後補銳化（會在前景物體產生 ringing）。實測也一致：
銳化強度 0/30/60/100 對應的偏差是 5.63/5.85/6.61/7.59，越銳化離理想越遠。
但這只說明「銳化不是抗鋸齒的解法」，不代表要關掉 —— 那是感知取捨，
合成測試圖（全是硬邊黑白）是銳化表現最差的場景，真實照片有紋理，價值在別處。

### 15.6 Lanczos 不是「最好」的選擇

Lanczos 靠負瓣換銳利度，代價是硬邊緣會 ringing。要「平滑」的話負瓣是扣分項。
而且 2.25 倍縮放下 Lanczos-3 每個目的像素要取樣約 14x14 個來源像素，
是面積平均的 20 倍。面積平均沒有負瓣，不可能 ringing。

### 15.7 分數覆蓋的成本來自「盒子重疊」，不是權重運算

改完之後縮放從 241 ms 變成 906 ms（3.75 倍）。我原本估「幾乎不花時間」，
理由是這段被匯流排卡住 —— 錯了，如果真的是匯流排受限，加算術不會變成 3.75 倍。

真正的原因是 `sx1` 改成無條件進位之後**相鄰盒子會重疊一個像素**：
2.25 倍下每個盒子從 2~3 格變成 3~4 格，走訪次數約 2.1 倍，再乘上每個樣本
多出的乘法與查表。

兩個優化把它救回一半（906 → 528 ms，畫質數值完全不變）：

- **反向 gamma 用查表，不要二分搜尋。** 原本每個目的像素三通道各八次帶分支
  迭代，480x800 就是九百多萬次難預測的分支。改成 4096 格的反查表（4KB，
  塞得進 D-Cache）。格子粒度 16，而最暗處相鄰 sRGB 階的線性差距約 20，
  暗部不會併階。
- **水平權重預先建表。** 同一組權重被 800 個目的列重複使用，原本每個來源樣本
  都現算一次 min/max/減法/移位。存成緊湊格式（偏移＋長度）而不是固定跨距 ——
  實際摸到的資料只有約 4KB，留得住快取；固定跨距要 19KB 就放不下。

### 15.8 隨機播放讓兩次執行不能直接比

相簿是隨機播放，每次抽到的照片尺寸分布都不同。連續三輪比較都得拿
「JPEG 解碼時間」當尺寸代理去估算，估出來的倍率從 1.7 到 2.4 都有。

**量測有樣本變異的系統時，一定要同時記錄一個規模指標。** 這裡加了累計來源
像素數（單位千像素避免溢位），之後就能算「每百萬像素幾毫秒」，跨批次直接比。

模型：`每張 ≈ 647 ms x 來源百萬像素 + 327 ms`。後面那個常數項是銳化＋抖動＋
旋轉，它做的是**目的地**（填滿時固定 480x800），不隨來源尺寸變 —— 把它也除以
來源像素數會重複計算，我第一次就是這樣把門檻算成 2.0 Mpx（實際是 2.6）。

### 15.9 讀執行中的系統，單張數值可能是撕裂的

用 SWD 讀正在播放的板子，`g_dbg_w` 可能來自第 N 張、`g_dbg_us_out` 來自第 N-1 張。
**只有累計值可信**（每張結束時才更新），單張的瞬時值不要拿來推理。

### 15.10 一個沒有效果的嘗試：PSRAM 改 write-back

原本整片 32MB 是 write-through 且 `NOT_BUFFERABLE`，等於每個 byte store 都是
獨立、同步、不能合併成 burst 的 PSRAM 交易。看起來像是重大瓶頸。

把純 CPU 暫存那半（0x91000000 以上 16MB：全尺寸 RGB、縮圖、播放清單、
資料夾索引、圖示備份）切成第 8 號區域改成 write-back。**端到端只賺約 3%。**

原因是瓶頸不在 store 的粒度，而在總流量。而 write-back 的 write-allocate
還多帶了一輪填線讀取（每張多 6.5MB），把省下來的抵銷掉大半。

保留這個設定（沒有壞處），但**別指望它**。真正的流量大頭是那個全尺寸 RGB888
中間層：被寫進 PSRAM 6.5MB、又被完整讀出來 6.5MB，而縮放對每個來源像素只用
一次。要省就得砍掉它（帶狀串流），不是調快取政策。

註：重疊時**編號大的區域優先**，所以覆蓋用的區域編號要大於底下那片。

### 15.11 換更好的濾波核是死路 —— 但要有對的尺才看得出來

問題：既然盒狀濾波在頻域上壓不乾淨超過 Nyquist 的成分，換 Mitchell 或
Lanczos 是不是能再降鋸齒？

**答案是不能，而且會更差。** 對「理論正確答案」的平均絕對差：

| 做法 | rings | star |
|---|---|---|
| 線性光盒狀（不銳化）| **14.33** | **4.79** |
| PIL 三次（Catmull-Rom）| 16.18 | 5.51 |
| 盒狀 + 銳化 100（本專案）| 16.62 | 5.62 |
| Mitchell + 銳化 100 | 17.45 | 6.14 |
| Lanczos-3 | 18.13 | 7.38 |

**越銳利的核離正確答案越遠。** 2.25 倍縮小的正確操作本來就是面積平均 ——
那正是感光元件在做的事。負瓣是為了「看起來銳利」刻意加入的失真，不是更正確。
所以縮小用盒狀／面積平均已經是對的，沒有升級空間。

### 15.12 用錯的基準會把對的方向判成錯的

這個結論一開始被我判反了，原因是基準選錯。

先前拿「線性光 Lanczos」當基準算平均絕對差。那把尺**獎勵銳利度**：
Mitchell 刻意用銳利度換無 ringing，於是分數更差（10.00 vs 盒狀 7.59），
我因此一度認定「Mitchell 實作有 bug」，還去追相位偏移、印權重表除錯 ——
權重其實完全正確。

**拿某個特定演算法當基準，等於預設它是對的。** 正確做法是回到問題本身：
測試圖樣是解析式定義的，直接在每個目的像素涵蓋的來源區域內超取樣
（6x6，線性光空間）求平均，那就是該像素應有的值，與任何演算法無關。
換上這把尺，排名整個反轉。

`test/groundtruth.py` 是這把尺。**任何「A 比 B 好」的畫質結論，先確認基準
不是 A 或 B 的近親。**

### 15.13 已經沒有剩餘空間了

換上正確基準之後回頭看本專案：盒狀+銳化 100 是 16.62、銳化關掉是 16.26、
PIL 的線性光盒狀是 14.33。銳化只佔 0.36；剩下約 1.9 的差距裡包含我們
刻意加的有序抖動（抖動用空間雜訊換掉色帶，逐像素比對一定會被扣分）
與邊界處理細節，有號平均只有 0.80，代表兩者沒有系統性偏差。

也就是說**重取樣這一段已經貼著理論極限了**。還想再降鋸齒只剩兩條路：
把銳化調低（很小，而且畫面會變軟），或者根本不要在板子上縮 ——
在 PC 上預先壓成顯示尺寸。實測比例 1:1 時本專案的重取樣器輸出與
「來源直接量化成 RGB565」**逐位元組相同**（100% 像素、最大誤差 0），
也就是完全不引入任何重取樣誤差。

### 15.14 研究級的「保細節」縮小演算法解的是相反的問題

查過三篇代表作：Kopf 2013（content-adaptive，讓取樣核隨影像特徵變形，EM 迭代）、
Öztireli & Gross 2015（以 SSIM 為目標函數，有封閉解、成本與線性濾波同級）、
Weber 2016（DPID，反向雙邊濾波，給偏離鄰域越多的像素越大權重）。

Öztireli 那篇是唯一在 MCU 上跑得動的，所以實作出來（`test/ssim_downscale.py`）
拿真實照片測。它的封閉解本質是**自適應局部對比補強**：縮小會壓低局部變異數，
它用 sqrt(輸入變異數/輸出變異數) 當增益把對比拉回去。

**結果是讓鋸齒更明顯。** 老鷹翅膀對天空那種高對比平滑邊緣，補強對比等於把
階梯的落差也放大。這類演算法的動機是「縮小把細節平均掉、照片變糊變平」，
跟「邊緣太硬有階梯感」是相反的訴求。

**專業軟體也沒有魔法**：Photoshop / Lightroom / ImageMagick 提供的就是
bicubic / Mitchell / Lanczos 這一家族加可選銳化，跟 15.11 量過的是同一批。

另外，「接近無損的縮小」在原理上不存在：1024 壓到 480 丟掉 78% 的取樣點，
資訊是可證明地消失的。那些論文做的不是「不損失」，是「選擇損失哪些」。

### 15.15 真實照片上唯一看得出差別的變數是銳化

合成圖樣（硬邊黑白）會誇大縮放演算法的差異、低估銳化的影響。改用真實照片
（`test/photos/`，從 picsum.photos 抓的 1200x1800）之後，把同一個高對比平滑
邊緣放大八倍並排比較，結論很乾脆：

- 換濾波核（盒狀 / Mitchell / SSIM 最佳化）：肉眼幾乎分不出來
- 銳化 100 / 60 / 30 / 0：邊緣的過衝亮暈與階梯感逐級消失，差異明顯

也就是說**要減少鋸齒不需要更強的演算法，需要少做一件事**。銳化的存在意義是
補償縮小造成的變軟，但它同時把邊緣過渡壓得更陡 —— 在 2.25 倍縮小後只剩
一兩個像素寬的邊緣過渡上，這個代價特別明顯。

判讀畫質時：**內容選錯會把結論帶偏**。合成圖樣適合量「誰比較接近正確答案」，
真實照片才判得出「使用者實際會看到什麼」。兩種都要。

## 十六、JPEG 硬體解碼：輪詢版量到的不是硬體速度

### 16.1 輪詢版是「CPU 逐字搬 FIFO」，比 DMA 慢 4.8 倍

`HAL_JPEG_Decode()`（輪詢版）的核心是
`while (JPEG_Process(hjpeg) == JPEG_PROCESS_ONGOING)`，而 `JPEG_Process` 就是
**CPU 手動搬運 JPEG 週邊的 FIFO**。同一張 2.16MP 的照片、同一塊板子：

| 路徑 | 每張 | 每 Mpx |
|---|---|---|
| `HAL_JPEG_Decode`（輪詢）| 305.6 ms | 141.5 ms |
| `HAL_JPEG_Decode_DMA` | **63.9 ms** | **29.6 ms** |

**相簿最初量到的 141 ms/Mpx 一直被當成「硬體解碼的成本」，其實那是 CPU
搬資料的成本。** 真正的硬體能力是 29.6 ms/Mpx —— 800x480 只要 11.4 ms，
足以支撐 20fps 以上的 MJPEG 播放。

一次只解一張的場景（相簿）用輪詢版是合理的取捨（少掉回呼與中斷設定），
但**不要把它量到的數字當成硬體極限**。

### 16.2 HPDMA 的區塊大小是 16 位元，而 HAL 直接遮掉不檢查

這是整件事裡最惡劣的陷阱。`DMA_CBR1_BNDT` 只有 16 位元（上限 65535 bytes），
而 HAL 的寫法是：

```c
MODIFY_REG(hdma->Instance->CBR1, DMA_CBR1_BNDT, (SrcDataSize & DMA_CBR1_BNDT));
```

**`& 0xFFFF` 遮掉，沒有任何檢查、沒有回傳錯誤。** 後果分兩種，第二種更糟：

| 傳入長度 | 遮完 | 症狀 |
|---|---|---|
| 10MB (`0xA00000`) | **0** | 硬體回報 USE（使用者設定錯誤），還算好查 |
| 618KB (`0x96FB2`) | 28594 | **不報錯，默默傳錯長度** |

第二種沒有任何錯誤訊息，資料就是不對，而症狀會出現在很遠的地方
（解出來的影像壞掉），完全不會聯想到 DMA 長度被截斷。

所以 **DMA 模式必須分塊餵**（本專案用 32KB），輸入靠 `GetDataCallback`、
輸出靠 `DataReadyCallback` 接續。ST 的 `JPEG_DecodingFromXSPI_DMA` 範例
用小緩衝區配回呼不是風格選擇，**是這個硬體限制逼出來的**。

註：這也修正了第 11.3 條的適用範圍。那條說「`DataReadyCallback` 裡不要呼叫
`HAL_JPEG_ConfigOutputBuffer`」，針對的是**輪詢模式下一開始就把整塊交出去**
的用法；**分塊 DMA 模式下在回呼裡接續餵緩衝區是本來就該做的事**。
用一個 `g_dma_mode` 旗標區分兩種行為。

### 16.3 別把實驗放進「每次都會執行」的路徑

第一版我把 DMA 通道設定與中斷啟用寫進 `HAL_JPEG_MspInit()` —— 那是照片路徑
每次都會走的初始化。結果輪詢解碼被干擾：**93 次失敗、1 次成功，相簿完全
不能用，而且重燒也救不回來**（壞的是每次都會執行的程式碼）。

正確做法：實驗的所有副作用關在一個函式裡，而且**由外部旗標觸發**
（用 SWD 寫 `g_dbg_bench_go`）。不觸發就完全等於不存在；出事重置一次就恢復。
測完做完整拆除：關中斷 -> `HAL_JPEG_Abort` -> `HAL_DMA_DeInit` 兩個通道 ->
解開 `hdmain`/`hdmaout` 連結 -> `HAL_JPEG_DeInit` + 重新 `Init` + 重建色彩表。
少做任何一步，之後的輪詢解碼都可能被影響。

還有一個相關的：**啟動了非同步硬體的失敗路徑一定要收乾淨**。DMA 啟動後
逾時就直接返回、沒有 `HAL_JPEG_Abort()`，週邊會停在忙碌狀態，之後每一次
解碼都拿到 `HAL_BUSY` —— 症狀是「第一張之後整個卡住」，看起來像解碼壞掉，
完全不會聯想到是先前那次失敗的實驗留下來的。

### 16.4 診斷靠硬體自己的錯誤碼，不要靠猜

DMA 接不起來時，把三個錯誤碼一起撈出來，一次就定位：

```c
g_dbg_bench_jerr     = HAL_JPEG_GetError(&g_hjpeg);   /* 4 = ERROR_DMA */
g_dbg_bench_derr_in  = HAL_DMA_GetError(&g_bdma_in);  /* 0 = 輸入正常 */
g_dbg_bench_derr_out = HAL_DMA_GetError(&g_bdma_out); /* 4 = ERROR_USE */
```

「輸入 0、輸出 USE」直接指向輸出通道的設定，而輸出長度正好是那個被遮成 0
的 10MB。**沒有這三個數字，我會在通道設定、埠分配、快取一致性之間繞很久。**

### 16.5 順帶：漏開 DMA 控制器時脈不會報錯

`__HAL_RCC_HPDMA1_CLK_ENABLE()` 在 ST 範例裡放在獨立的 `MX_HPDMA1_Init()`，
很容易漏。漏了的話 `HAL_DMA_Init()` 寫暫存器等於寫進虛空，**而且照樣回傳
`HAL_OK`** —— 症狀是設定看起來成功、傳輸永遠不開始。

### 16.6 DMA 在隔離模式完全正確，整合進正式路徑卻會卡死（未解）

隔離模式下驗證得非常乾淨：

| 檢查 | 結果 |
|---|---|
| 輸出長度 | 輪詢 6,480,000 = DMA 6,480,000 |
| 逐位元組比對 | **完全相同** |
| 校驗和 | 兩邊都是 `0x3D190426` |
| 連續 40 次 DMA 解碼 | **40 次全過、0 失敗** |
| 速度 | 30.7 ms/Mpx（輪詢是 141.5） |

**但整合進正式路徑就壞**：第一張成功，之後 `HAL_JPEG_Decode_DMA` 永遠回傳
BUSY，而且 `HAL_JPEG_Abort()` 救不回來 —— 連退回輪詢也一起失敗
（實測 `dma_ok=1`、`dma_fallback=1042`、`decode_ok=3` 對 `decode_fail=517`）。

兩者唯一的差別是**兩次解碼之間夾了什麼**：隔離測試是背對背連續呼叫，
正式路徑中間隔著 SD 讀檔、轉色、縮放、顯示與兩秒等待。根因還沒找到。

已經排除的：分塊邏輯本身（逐位元組驗證過）、連續次數（40 次沒問題）、
`ConfigOutputBuffer` 的無條件呼叫（ST 範例也是這樣寫）。

**教訓：「隔離測試全過」不等於「可以整合」。** 這個案例裡隔離測試涵蓋了
正確性、穩定性、效能三項，全部通過，整合後仍然壞 —— 因為它沒有涵蓋
「解碼之間發生的事」。設計隔離測試時要問的是「正式路徑有什麼是這裡沒有的」。

自動退回的設計值得保留：正式路徑先試 DMA、失敗就 Abort 並改用輪詢，
並記錄 `dma_ok` / `dma_fallback` / `dma_lasterr`。**這讓「實驗失敗」變成
「效能退回」而不是「功能損壞」**，而且失敗的頻率與時機直接顯示在計數器上。
（可惜這次連輪詢都被拖垮，所以最後仍然要整個退掉。）

### 16.7 順帶：自動開播讓除錯循環快很多

這塊板子沒有 UART，每次驗證都要「燒錄 -> 手動勾資料夾 -> 按開始 -> 等播放」。
一個 session 下來重複十幾次，而且中間的手動步驟沒有任何除錯價值。

`AUTO_PLAY`（`album_main.c`）讓掃描完直接開播，資料夾本來就預設全選 ——
插電就會動。相框本來就該是這個行為，順便讓遠端除錯不再需要人在旁邊。
往下滑回選單之後就走正常的手動流程，設定隨時改得到。

### 16.8 找到了：JPEG 週邊會累積狀態，Abort 清不掉，要 DeInit+Init

16.6 那個「連續 N 次 DMA 解碼後永久 BUSY」的未解問題，在影片專案裡解開了。

**症狀有高度一致性**：相簿是第 8 張、影片是第 24 格，之後
`HAL_JPEG_Decode_DMA` 永遠回傳 BUSY。次數不同但模式相同 —— 成功若干次後
突然永久卡死，而且**`HAL_JPEG_Abort()` 救不回來**（兩邊都試過）。

**解法是每次解碼後做完整的 DeInit + Init**：

```c
(void)HAL_JPEG_DeInit(&g_hjpeg);
g_hjpeg.Instance = JPEG;
(void)HAL_JPEG_Init(&g_hjpeg);
```

加上之後影片從「卡在第 24 格」變成連續播放數百格不停。成本每格幾十微秒，
相對於整格 70ms 可以忽略。

**所以是狀態累積而不是單次操作沒收乾淨**。真正累積的是什麼還沒查明
（懷疑跟「解碼結束時 HAL 會再呼叫一次 DataReadyCallback、而我們在那裡又餵了
一塊輸出緩衝區」有關），但 DeInit+Init 是可靠的繞法。

**同時修正 16.6 裡一個錯誤的推論。** 當時的隔離測試「連續 40 次全過」被我
讀成「穩定」，但那個測試是**跑固定 40 次就停**，根本沒證明第 41 次會成功。
影片這邊在第 24 格就失敗，回頭看那個 40 次很可能只是還沒撞到。
**固定次數的壓力測試只能證明「至少撐得住 N 次」，不能證明穩定** ——
要證明穩定得跑到失敗為止，或跑到遠超過實際用量的次數。

### 16.9 MJPEG 播放的實際瓶頸是轉色，不是解碼

800x480 的 4:2:0 影格，實測 499 格的平均：

| 階段 | 每格 | 佔比 |
|---|---|---|
| JPEG 解碼（DMA） | 2.5 ms | 3.6% |
| **YCbCr -> RGB 轉色（CPU，jpeg_utils）** | **64.0 ms** | **91.4%** |
| 換頁（等垂直消隱） | 1.9 ms | 2.7% |
| 合計 | 70.0 ms | **14.3 fps** |

**解碼只佔 3.6%**，而且比先前從相簿照片推算的 11.4 ms 還快 4.5 倍 ——
因為影片影格是 4:2:0（每像素 1.5 bytes），相簿那批照片是 4:4:4（3 bytes），
輸出資料量只有一半。**跨取樣格式外推是不可靠的。**

轉色佔 91%，而 DMA2D 支援 YCbCr 輸入（16.2 查證過）。這是下一步唯一該做的
最佳化 —— 使用者最初提的「用 DMA2D 做 YCbCr→RGB」在照片上只值兩成
（board-notes 15 那輪），在影片上值九成。**同一個想法，換個場景就從邊際
效益變成決定性槓桿。**

### 16.10 HAL_DMA2D_Start 只能用一次 —— 除非你也用 PollForTransfer

這個 bug 的欺騙性極高，值得完整記下來。

**症狀**：畫面在「第一格畫面」與「全黑」之間快速交替閃爍。

**已排除的（都量過）**：雙緩衝索引沒寫反（`g_front` 確實在翻，兩塊的寫入
次數 564 對 568 完全平衡）、LTDC 沒有 FIFO underrun（計數 0）、
DMA2D 設定完全正確（輸入 YCbCr、CSS=4:2:0、輸出 RGB565、800x480、無錯誤旗標）。

**根因**：`HAL_DMA2D_Start()` 會把 `hdma2d.State` 設成 BUSY，而負責設回 READY 的
是 `HAL_DMA2D_PollForTransfer()`。但 3.3 那條說過那個函式不可靠（等待迴圈包在
`if (CR & START)` 裡，快速傳輸會被整個跳過），所以我們改成自己輪詢 START 位 ——
**代價是 State 永遠停在 BUSY，第二次之後 HAL_DMA2D_Start 直接回傳 HAL_BUSY
什麼都不做**。而回傳值被 `(void)` 丟掉，完全沒有錯誤跡象。

所以程式邏輯正確地輪流指定兩塊 framebuffer，硬體的 `OMAR` 卻永遠停在第一次
那個位址，另一塊從頭到尾沒被寫過。

**解法**：每格直接寫暫存器啟動，完全不碰 HAL 的狀態機。Init/ConfigLayer
仍可用 HAL（一次性、不涉及狀態機）。

```c
DMA2D->FGMAR = src;  DMA2D->OMAR = dst;
DMA2D->NLR   = (w << DMA2D_NLR_PL_Pos) | h;
DMA2D->IFCR  = DMA2D_IFCR_CTCIF | DMA2D_IFCR_CTEIF | DMA2D_IFCR_CCEIF;
DMA2D->CR   |= DMA2D_CR_START;
while ((DMA2D->CR & DMA2D_CR_START) != 0u) { }
__DSB();
```

這其實是 3.3 早就給過的結論（相簿的 dma2d.c 一直是直接寫暫存器），
但我在新專案裡用了 HAL 的便利介面，就重新踩了一次。
**「同一個坑在不同專案裡會換一種樣子出現」** —— 3.3 記的是「等待不可靠」，
這次現形的是「狀態機卡死」，兩者是同一個根因的不同面向。

**找到它的關鍵是量測而不是讀碼**：程式邏輯看起來完全正確，只有把硬體的
`OMAR` 讀出來（永遠是同一個位址）跟軟體的計數（兩塊平衡）擺在一起，
矛盾才浮現。

### 16.11 更正 16.9：DMA2D 轉色不是「四千倍」

16.9 曾記錄「轉色從 64ms 變成 0.016ms」。**那是假的** —— 當時 DMA2D 因為
上述的 HAL_BUSY 根本沒執行，量到的是「什麼都不做」的時間。

修好之後的真實數字（800x480 4:2:0，1101 格平均）：

| 階段 | CPU 轉色 | DMA2D |
|---|---|---|
| 解碼 | 2.5 ms | 2.7 ms |
| 轉色 | 64.0 ms | **20.9 ms** |
| 換頁＋等待 | 1.9 ms | 18.8 ms |
| 合計 | 70.0 ms | **42.4 ms** |
| 能力 | 14.3 fps | **23.6 fps** |

DMA2D 讓轉色快 3 倍（不是 4000 倍），整體從 14.3 到 23.6 fps。仍然達成
20 fps 的目標，但餘裕遠比原本以為的小。

轉色 20.9ms 換算是 64 MB/s（讀 576KB + 寫 768KB），而 LTDC 同時持續佔用
46 MB/s —— **現在的瓶頸是 100MHz PSRAM 的頻寬，不是運算**。想再快就得
減少 PSRAM 往返（例如 YCbCr 中間緩衝區放內部 SRAM）。

**教訓：效能數字好得不合理時，先確認那段程式真的執行了。** 四千倍的加速
應該立刻引起懷疑 —— 我當時直接寫進了 commit 訊息與 board-notes。

### 16.12 分塊餵資料時，每一塊的長度都必須是 4 的倍數

影片有 26% 的影格解碼失敗（`jerr = HAL_JPEG_ERROR_DMA`）。根因是**餵給輸入
DMA 的最後一塊只有 1~3 個位元組**，而 HPDMA 的來源／目的資料寬度設成 word，
`BNDT` 不是 4 的倍數硬體就報 USE（user setting error）。

**HAL 在兩個地方對長度的處理方向相反**，這是陷阱的核心：

| 位置 | 做法 |
|---|---|
| `JPEG_DMA_StartProcess`（第一塊）| **捨去**：`len - len % 4` |
| `JPEG_DMAInCpltCallback`（續傳）| **進位**：`((len + 3) / 4) * 4`，但**只在 `len >= 4` 時**；`< 4` 是「Nothing to do」 |

於是：整包一次餵完的小影格，第一塊被捨去成 4 的倍數，`size % 4` 個位元組被
留到下一次；那個尾巴只有 1~3 個位元組，HAL 不幫忙進位，原封不動送進 DMA。

失敗集合完全可預測，實測 120 格：

| 影格類型 | 數量 | 失敗 |
|---|---|---|
| 單塊（`size <= CHUNK`）且 `size % 4 != 0` | 32 | **32（每一次都失敗）** |
| 單塊且 `size % 4 == 0` | 16 | 0 |
| 分塊（`size > CHUNK`，尾段夠長會被進位） | 72 | 0 |

32/120 = 26.7%，跟量到的失敗率完全吻合。

**解法**：自己保證每一塊都是 4 的倍數，不要相信 HAL 會處理。
影格包本來就把每格補齊到 4 位元組邊界，所以往上取整讀到的是補的 0，
而且落在 EOI 之後，解碼器不會理它。

```c
n = (n + 3u) & ~3u;                       /* 續傳的每一塊 */
first = (size > CHUNK) ? CHUNK : ((size + 3u) & ~3u);   /* 第一塊 */
```

**順帶修掉另一個違反協定的地方**：輸入用完時我們是直接 `return`，
但 HAL 的說明寫得很清楚 —— 要用 `HAL_JPEG_ConfigInputBuffer(hjpeg, ptr, 0)`
明講「沒有了」。直接 return 的話 `pJpegInBuffPtr` 與 `InDataLength` 都留著
上一次的值，而 `JPEG_DMAInCpltCallback` 只檢查 `InDataLength > 0` 就重啟
DMA，等於**把同一塊資料再送一次**。

修完：1940 格連續播放，**失敗 0**，`late` 從 406 變成 0，輸出長度每格都是
576,000 bytes（800x480 的 4:2:0，完整不截斷）。

#### 定位方法：先證明它是確定性的，再問「哪幾個」

這個 bug 值得記的不只是結論，還有找法。一開始手上只有「26% 失敗」，
看起來像競爭條件（每格中間夾著轉色、換頁、等待，很容易往那邊想）。

**第一步是算出它不是隨機的**：`fail / (fail + ok)` 除以圈數，得到 32.0 和 88.0
兩個整數 —— 120 格裡固定 32 格每圈都失敗。兩次取樣都給同一個數字。
確定性的 bug 和競爭條件要用完全不同的方法追，這一步省掉了整條錯路。

**第二步是讓硬體自己說是哪 32 格**：加一個位元圖（120 格 = 4 個字），
每格成功/失敗各設一個位元，一次 SWD 讀取就拿到完整的失敗集合。
`failmap & okmap == 0`（完全互斥）本身就再次證明了確定性。

**第三步是凍結第一次失敗的現場**：`CSAR / CBR1 / CTR1 / CSR` 加上 HAL 的
`InDataLength`、`pJpegInBuffPtr`。讀出來 `CBR1 = 2`、`CTR1` 是 word 寬度，
USE 的原因當場就寫在暫存器上，不必猜。**只留第一次**——後續的失敗會覆蓋掉，
而且錯誤碼會被之後的 DeInit/Init 清成 0。

拿到失敗集合之後，跟影格表對一次 `size % 4` 就收工了。
**「26% 失敗」和「這 32 格因為 size 不是 4 的倍數所以必定失敗」是同一件事，
但後者可以直接寫成修正。**

## 十七、SD 卡：從電腦把大檔送進板子

沒有讀卡機時，可以讓板子當中介：SWD 把資料塞進 PSRAM，韌體收一塊寫一塊到卡上。
這一章記的是這條路上實際踩到的東西。

### 17.1 SWD 的實際吞吐量

| 設定 | 4MB 耗時 | 換算 |
|---|---|---|
| `freq` 未指定（預設 8000 kHz） | 7.82 s | 536 KB/s |
| `freq=24000`（ST-LINK V3 上限） | 4.69 s | **895 KB/s** |

`freq=50000` 會被夾到 24000，沒有更快。122MB 約三分鐘，一次性作業可以接受。

目的地寫 PSRAM（`0x91000000`）可行，前提是韌體已經把 XSPI 設成記憶體映射。

### 17.2 `-w32` 的回寫驗證會跟「韌體吃掉指令」打架

主機用 `-w32` 寫一個指令字給韌體，韌體處理完把它清成 0 —— 而 CLI 寫完會**讀回來
驗證**，於是驗證必然對不起來、**CLI 回傳非零**。腳本有 `set -e` 就會在這裡無聲中止。

症狀非常難查：trace 停在 CLI 那一行，沒有任何錯誤訊息（輸出被 `>/dev/null` 丟掉）。

**韌體把指令字清掉正是「做完了」的信號**，所以這個「失敗」要容忍：

```bash
wr32() { conn -w32 "$1" "$2" >/dev/null || true; }
```

真正的成功與否要靠自己的握手（輪詢指令字歸零 + 檢查錯誤碼）判斷，不要靠 CLI 的回傳值。

順帶一提，CLI 印的十六進位是**大寫**，`[ "$v" != "0000000a" ]` 這種比對會永遠成立。
一律轉小寫再比。

### 17.3 指令與參數要合併成一個字

「先寫長度、再寫指令」中間隔著一次完整的 SWD 連線（約 1.5 秒），韌體很可能在
兩者之間就讀到了半套狀態。把它們塞進同一個字就沒有這個問題：

```c
g_sdw_cmd = (opcode << 28) | payload;   /* payload 28 位元，蓋得住 16MB */
```

### 17.4 `FATFS_LinkDriver` 第二次呼叫一定失敗

FatFs 只有一個磁碟槽。播放路徑開機時已經掛接過同一個驅動，之後要進燒錄模式
再掛接一次就會失敗。**這不是錯誤，是常態** —— 直接沿用 `"0:"` 就好。

第一版在這裡 `for(;;){}` 卡死，症狀是「燒錄模式永遠不就緒」。

### 17.5 沒有來源時**不能**停在空轉迴圈

第一次使用時卡上還沒有影片檔，Flash 也是空的。如果這時候韌體停在
`for(;;){}`，主機就沒辦法把它叫進燒錄模式 —— 變成「要有影片才裝得進影片」的
雞生蛋問題。找不到來源的閒置迴圈裡一定要繼續輪詢燒錄旗標。

### 17.6 偵錯器寫進去的資料，CPU 讀之前要失效快取

主機經 SWD 寫 PSRAM 是**完全繞過 CPU 的 D-Cache** 的。接著 FatFs 會用 CPU 去讀
那塊記憶體交給 SD，讀到的可能是上一輪殘留在快取裡的舊內容。

跟第 3.1 條那個 DMA2D 的坑同一類：**硬體（這裡是 SWD）寫、CPU 讀，一定要手動失效**。
位址與長度都要對齊到 32 位元組的快取列。

```c
SCB_InvalidateDCache_by_Addr((uint32_t *)SDW_BUF, (int32_t)((len + 31u) & ~31u));
```

### 17.7 未解：連續的單磁區 FAT 寫入會讓卡片停止回應

**建立新檔案沒問題**（實測連續寫入 4.58MB 完全成功）。但用
`f_open(FA_CREATE_ALWAYS)` 覆寫一個已經存在的檔案時要先釋放整條簇鏈，
這會產生大量**單磁區**的 FAT 寫入，連續約 130 次之後卡片就不再回應。

現場（靠 `g_sd_*` 那組變數撈出來的）：

| 量到的 | 值 |
|---|---|
| `BSP_SD_WriteBlocks` 回傳 | -4（PERIPH_FAILURE） |
| `HAL_SD_GetError` | 4 = **CMD_RSP_TIMEOUT** |
| `hsd.State` | 1 = READY（軟體狀態正常） |
| `BSP_SD_GetCardState` | BUSY |
| 失敗磁區 | 6124 / 6126（兩次獨立實驗，都在 FAT 區且相鄰） |

**已排除的**：
- 唯讀保護 —— `g_sd_writes` 有在增加，寫入確實有發生
- HAL 狀態機卡死（第 16.8/16.10 那一類）—— `hsd.State` 是 READY，不是 BUSY
- 快取一致性 —— `HAL_SD_WriteBlocks` 是 **CPU 輪詢 FIFO**，不走 DMA，
  緩衝區在哪個快取政策的區域都不影響

還沒查明是卡片本身有弱點、SDMMC 時脈餘裕不夠，還是 busy 處理不足。

**教訓：不要拿有資料的卡反覆試這個。** 失敗發生在 FAT 區，中途失敗的
`remove_chain` 有可能讓檔案系統處於不一致的狀態。要追這個問題請先換一張空白卡。
（這次實測下來檔案系統本身沒壞 —— 掛載與 `f_open` 都正常，
只有被覆寫的那個檔案變成 0 長度 —— 但那是運氣，不是設計。）

### 17.8 一個對比很有價值的觀察

同一張卡、同一套程式：
- **讀取**：數千次零錯誤
- **大塊循序寫入**：4.58MB 一次過
- **密集單磁區寫入**：約 130 次後死

三者的差異本身就是線索：問題不在「能不能寫」，而在**寫入的節奏與粒度**。
下次追這個先從「每次寫入之間強制等到 `SD_TRANSFER_OK` 並加最小間隔」開始，
而不是從卡片品質開始懷疑。
