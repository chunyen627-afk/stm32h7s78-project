# STM32H7S78-DK 電子相簿

讀 SD 卡上的照片，隨機輪播。全繁體中文介面，觸控操作。

## 功能

- **勾選最上層資料夾**播放（最多 64 個），底下**所有子層**的照片都會撈進來，
  上限 8,192 張、單張 3.4MP，JPEG baseline 4:4:4 / 4:2:2 / 4:2:0。
  資料夾多的時候清單可以**上下拖曳捲動**
- **播放順序**可選隨機（預設，每輪重洗）或循序（照掃描順序，通常等於時間順序）
- 間隔 **2~5 秒**可調（預設 2 秒）；解碼與顯示重疊，只要解碼快過間隔，
  設定值就是實際展示時間（見下方「效能」）
- **完整顯示**：照片一律不裁切，比例不合就留黑邊
- **顯示方向**可選直立 / 橫向 / **自動（預設）** —— 橫式照片切到橫向可以從
  480x320 放大到 720x480，面積 2.25 倍
- **我的最愛**：暫停時點愛心收藏這張，選單底下多一顆「最愛」就能只播收藏的。
  清單存在卡上的 `我的最愛.txt`（純文字，電腦上打得開），**每次收藏只寫
  兩個磁區**。再點一次愛心取消，誤點救得回來。詳見下方「我的最愛」
- **MJPEG 影片播放**：卡上的影格包（`*.bin`）會列進選單，無限循環播放。
  影片清單同樣可以捲動。做法見 [projects/video](../video)
- **隨身碟模式**：USB1 插上電腦，板子自動變成隨身碟，SD 卡直接掛給電腦，
  不用拔卡；拔線自動回相簿並重新掃卡。詳見 [projects/usbdrive](../usbdrive)
- **記憶卡熱插拔**、掃描進度顯示、看門狗（16 秒）防卡死
- **記憶卡停止回應時會自動恢復**：連續 24 張解不開就判定卡片掛了，
  自己把 SD 斷電重新初始化，不會停在那裡空轉（見下方「記憶卡不回應時」）
- 對記憶卡**預設只讀**，磁碟層回報寫入保護。唯一的例外是收藏，
  而且只在那一瞬間解開、只碰 `我的最愛.txt` 一個檔案（見下方「寫入安全」）

### 操作

全部走觸控。實體鍵只留背光與暫停，因為這塊板子只有一顆 USER 鍵。

| 情境 | 操作 | 效果 |
|---|---|---|
| 選單 | 點資料夾 | 勾選／取消 |
| 選單 | 清單上下拖曳 | 捲動（資料夾多的時候） |
| 選單 | 開始播放 / 最愛 / 影片 | 播勾選的資料夾／只播最愛／進影片清單 |
| 播放中 | **點一下畫面** | 暫停，並叫出疊加層 |
| 暫停中 | **點一下畫面** | 繼續播放 |
| 暫停中 | **往左拉** | 上一張 |
| 暫停中 | **往右拉** | 下一張 |
| 暫停中 | 拖下方拉桿 | 跳到大概的位置（粗調） |
| 暫停中 | 左上「返回」 | 回選單 |
| 暫停中 | 上排第二顆 | 方向切換：自動 ⇄ 固定 |
| 暫停中 | **上排愛心** | 空心＝加入最愛，實心＝移出最愛 |
| 任何時候 | USER 短按（<0.6 秒）| 背光 100 → 50 → 20 → 6 → 0% 循環 |
| 任何時候 | USER 長按（≥0.6 秒）| 暫停 / 繼續 |

暫停時的疊加層跟影片播放器是同一套版面，加上愛心之後是四顆
（4×100px + 5×16px 間距 = 480，剛好排滿窄邊）：

```
返回    自動/直立/橫向    ♥    暫停

              （照片）

     ├──────●─────────┤
     2000              4254
```

三秒後疊加層自己收起來，但**維持暫停** —— 收起只是讓照片看得完整。

**拉桿與左右拉是互補的，不是二選一**：四千多張攤在 400px 的拉桿上，
一個像素等於十張，所以拉桿只能粗調；要精準前後一張就用左右拉。

原本的全螢幕滑動手勢（左右翻頁、下滑回選單、上滑切方向）已經移除 ——
手勢好用但**看不見**，第一次拿到相框的人不會知道有這回事。

### 顯示方向

面板實體是 800x480 橫向，預設把邏輯 480x800 的直立畫布轉上去。切成橫向時
畫布變 800x480：

| 照片 | 直立 | 橫向 |
|---|---|---|
| 橫式 3:2 | 480x320 | **720x480** |
| 正方形 | 480x480 | 480x480 |
| 直式 2:3 | 480x720 | 320x480 |

**軟體只改「照片怎麼畫」，不會轉動面板。** 切到橫向後畫面上的內容是躺著的，
要看起來正常必須把相框**實體轉 90 度** —— 板子上沒有加速度計，軟體無從得知
目前的擺放方向。

所以「自動」（依每張照片的長寬比決定，**預設值**）適合**拿在手上翻看**，
可以跟著轉手；**立在桌上播放**建議固定直立或橫向，否則相框不會自己轉，
會有一半照片躺著。

暫停中點上方中間那顆就能在「自動」與「固定」之間切換 —— 離開自動時會
**凍結在目前這張的方向**，你看到什麼就固定什麼，畫面不會按一下就翻掉。
選單裡也有同一個設定，開機時可以先設好。

**疊加層本身不跟著轉**，永遠在窄邊那側的固定位置。會轉的只有照片。

## 我的最愛

暫停時點上排的愛心就收藏這張照片，再點一次取消。選單底下會多一顆「最愛」
（收藏數 0 時不顯示），按下去就只播收藏的那些。

收藏清單存在卡的根目錄 `我的最愛.txt`，純文字，在電腦上用記事本打得開 ——
一行一個照片路徑。

### 為什麼是清單而不是複製照片

第一版真的是把照片**複製**到 `我的最愛` 資料夾，理由是「卡插到電腦上也看得到
那些照片」。功能做出來也驗證過（連續四次操作零失敗、長度逐位元組相符），
但實際用起來有三個問題：

| | 複製照片 | 清單（現在） |
|---|---|---|
| 每次收藏的寫入量 | 一張 600KB ≈ **1200 個磁區** | **2 個磁區** |
| 數量上限 | 約 200 張（目錄簇的限制） | 256 張（清單容量，可調） |
| 佔空間 | 重複佔一份 | 64 KB 固定 |
| 選單即時更新 | **要重開機**（掃描只在開機做） | 馬上 |
| 電腦上看到什麼 | 真正的照片資料夾 | 一份文字清單 |

決定性的是第一項。當時那張 8GB 卡在連續寫入下會進 BUSY 就不再回應
（board-notes 20，後來確認是卡片壞了，已經換掉）—— 但**就算換上健康的卡，
「每收藏一張就打一千多次磁區寫入」仍然沒有道理**，何況卡上放的是使用者的
相簿。第三項則是使用者第一次用就踩到的。

### 固定寬度的紀錄

清單檔是 **256 筆 × 256 bytes = 64KB，大小從頭到尾不變**。收藏或取消只要
`f_lseek` 到那一格覆寫 256 個位元組，FatFs 就只做一個磁區的
read-modify-write —— **不配置新簇、不釋放簇鏈、不動 FAT**。
而釋放簇鏈正是 board-notes 17.7 把這張卡搞到不回應的動作。

版面刻意做成「一筆＝一行」：路徑後面補空白到 254，最後接 CRLF，
所以記事本打開就是一行一個路徑，空的格子是空行。

### 寫入安全

卡上是使用者真正的相簿，所以（`app_src/favorites.c`）：

- 磁碟層**預設唯讀**（`STA_PROTECT`），只有 `favorites.c` 會解鎖，動完立刻鎖回去。
  實測開機到播放全程 `g_sd_writes = 0`
- **只碰 `我的最愛.txt` 這一個檔案**。沒有 `f_unlink`、沒有目錄走訪、沒有遞迴
- 建立清單檔用 `FA_CREATE_NEW`，不用 `CREATE_ALWAYS`（後者會先釋放舊檔的簇鏈）
- 寫完**讀回來比對**才算成功。回傳 OK 不等於卡片真的收下了
- 卡上寫失敗時記憶體裡的清單會還原，不會出現「畫面說收藏了、卡上沒有」

### 清單檔不見或壞掉時

- 不存在 -> 開機自動建一個空的（64KB 一次寫完，7 次 `disk_write`，
  是大塊循序寫入那條安全路徑）
- 長度不對（被改過）-> 當作沒有清單，愛心變成不可按，**而且不會重建**。
  在電腦上刪掉它，下次開機才會建一個乾淨的
- **開機讀不到（`FR_DISK_ERR` 之類）-> 什麼都不做。** 這裡踩過一個會掉資料
  的坑：原本「`f_open` 失敗就建新檔」，把「這一瞬間讀不到」也當成「檔案
  不存在」，卡片閃一下就用 `FA_CREATE_NEW` 造了個空清單 —— 使用者 41 筆
  收藏變成 1 筆。現在只有 `FR_NO_FILE` / `FR_NO_PATH` 才建
- 清單裡的照片都不在卡上（換過卡、搬過檔案）-> 按「最愛」會提示，不會進到
  空的播放

## 隨身碟模式（相簿這邊做了什麼）

完整說明在 [projects/usbdrive](../usbdrive)，這裡只記相簿負責的部分 ——
因為**偵測與跳轉都在相簿裡**，不在那個目錄的程式碼中。

- `app_src/vbus.c` 用 ADC2 通道 6（PF14）量 CN18 的 VBUS。
  刻意不呼叫 `BSP_USBPD_PWR_VBUSGetVoltage()` —— 那要先跑
  `BSP_USBPD_PWR_Init()`，會把整套 USB-PD 拉進相簿
- `watchdog_feed()` 裡偵測（那是全域最常被呼叫的地方，涵蓋所有狀態），
  **連續一秒有電壓**才動作，而且**正在寫「我的最愛」時不切換**
  （直接問既有的 `sd_bsp_write_unlocked()`，不另外發明旗標）
- `app_src/usbdrive.c` 在 **DTCM `0x20004000`** 留暗號後重置。
  **不能放 AXI SRAM** —— bootloader 的堆疊在 `0x24072000`，往下長會踩掉它，
  症狀是「時好時壞」（board-notes 22.5）
- 真正的跳轉在 `main()` 的**第一行**（由 `tools/patch_project.py` 植入）。
  放在 `album_run()` 裡試過，跳得成功但 USB 不會列舉
- bootloader 的 `SystemClock_Config` 補開了 **HSE**（同樣由 patch 植入）。
  少了它 USB PHY 沒有時脈，症狀是「app 在跑、中斷正常、SD 讀得到，
  就是電腦看不到裝置」

## 記憶卡不回應時

這張卡在連續寫入下偶爾會進 BUSY 就不再回應，而**之後連讀取都會失敗**。
沒有處理的話症狀是「整個相簿卡死」：每張照片都解不開，翻頁迴圈把整份清單
試一遍再重來，迴圈裡有乖乖餵狗所以看門狗也不會救 —— 實測 `g_decode_fail`
衝到 1,511,732。

現在有三道：

- `sdbsp_read()` 一進來就餵看門狗。**讀取的失敗路徑以前走不到 `sd_wait_ready()`**，
  所以 16 秒的看門狗會先把板子打掉，下面兩道根本沒機會跑
- 連續 24 張解不開就判定卡片掛了（`g_card_sick`），跳出播放迴圈
- `card_recover()`：`f_mount(NULL)` 丟掉快取 -> `BSP_SD_DeInit()` 把 SDMMC
  斷電 -> 等 1 秒 -> 外層迴圈重新掛載並掃描

看門狗真的觸發時也不再停在「請拔出記憶卡再重新插入」等人來拔卡，
改成自己 `BSP_SD_DeInit()` 再試一次。**相框放桌上自己卡死、要人來拔卡
才會動，是最糟的失敗模式。**

## 除錯與自動測試

板子沒有 UART，狀態一律靠全域變數 + SWD 讀（燒錄 `mode=UR`、觀察 `mode=HOTPLUG`）。
旗標**不寫就完全等於不存在**，正式路徑一行都不會多跑（board-notes 16.3）。

| 旗標 | 作用 |
|---|---|
| `g_dbg_favtest = N` | **最愛的自動測試**：挑 N 張平均散布的照片收藏，再用最愛模式全部播一遍 |
| `g_dbg_wrtest = N` | **純寫入壓力測試**：對一個沒在用的格子反覆寫 N 次。不含任何最愛邏輯 |
| `g_dbg_sdclkdiv = N` | 覆寫 SDMMC 的 CLKDIV（2=High Speed、4=BSP 預設、8=再半）。改完要 `g_dbg_cardreinit = 1` 才生效 |
| `g_dbg_wrspread = 1` | 壓力測試改成每次寫不同的格子（散開磁區） |
| `g_dbg_cardreinit = 1` | 重新初始化記憶卡（換時脈之後用） |
| `g_dbg_inject = <PAUSE_*>` | 當成按了疊加層那一顆（`6` = 愛心） |
| `g_dbg_autoplay = 1` | 跳過選單直接開播 |
| `g_dbg_autovideo = 1` | 直接播第一部影片 |
| `g_dbg_fakedirs` / `g_dbg_fakevids` | 記憶體內的假清單，測捲動用，**不會動到卡片** |

`g_dbg_favtest` 的結果在 `g_dbg_ft_*`：`added`（收藏成功幾張）、`err` / `failat`
（第一次失敗的錯誤碼與位置）、`order`（最愛模式建出幾張）、`shown` / `showfail`
（實際播出幾張）、`wr`（整輪用掉幾次 `disk_write`）。

**做成韌體端而不是用 SWD 一步一步戳**，是因為每次 SWD 連線要一秒多，
戳十幾步就好幾十秒，而且**節奏跟使用者用手點完全不同** —— 實際遇到的失敗
正是連續操作才出現的，慢慢戳反而重現不了。

這個測試上線第一次跑就抓到「路徑含空白比對失敗」（見下方踩過的坑）。

## 音訊（WM8904 / I2S6 / 耳機孔 CN16）

**目前只有第一步：測試音。** 從 RAM 播一段自己產生的正弦波，證明
BSP + I2S6 + WM8904 這條鏈路是通的。串流 WAV、與影片同步都還沒做。

觸發方式（**請求放 DTCM，不是全域變數**）：

```bash
# 在重置點寫入「播 440Hz」的請求，然後讓核心跑
STM32_Programmer_CLI -c port=SWD mode=UR -w32 0x20004060 0x5A5A01B8 -run
```

請求的格式是 `0x5A5A0000 | Hz`。要加識別碼是因為燒錄用的 external loader
會把 DTCM 洗成隨機內容，剛好落在合法範圍就會誤觸發。韌體吃掉請求後會把它清成 0。

結果放在同一塊 DTCM（重置洗不掉，所以 `mode=UR` 讀得到）：

| 位址 | 內容 |
|---|---|
| `0x20004064` | 走到哪一步的位元圖，全部走完是 `0x3FE` |
| `0x20004068` | `BSP_AUDIO_OUT_Init` 的回傳值（`0xFFFFFFFF` = **這段程式根本沒執行**）|
| `0x20004074` | `BSP_AUDIO_OUT_Play` 的回傳值 |
| `0x200040F4` | **音訊 DMA 的中斷次數** —— 這個一直在跳才代表真的在播 |
| `0x20004164` 起 | WM8904 的暫存器（第一個是 ID，應該讀到 `0x8904`）|

**「DMA 在跑」跟「聽得到」是兩件事。** 實測 DMA 中斷持續在跳、編解碼器
每一級都正確，但音量給 40 就是聽不到 —— 所以 `audio_init()` 會明確再呼叫一次
`BSP_AUDIO_OUT_SetVolume`，不依賴 `Init` 的 `cfg.Volume`。

這條路上的四個根因（每一個的症狀都不指向原因）記在 board-notes 第二十三章：
PLL2 是 XSPI 的、PLL3 是 LCD 的、少一個中斷向量、DMA 連結串列節點的快取。

### 影片的聲音

影片會自動播**同名的 .wav**（`MOVIE10.bin` -> `MOVIE10.wav`）。沒有同名檔的
影片照舊只放畫面 —— 音訊不是播放的前提。

播放中點一下畫面叫出控制列，進度條上方有 －／＋ 兩顆音量鍵，一點調 10。
**音量 0 是真的靜音**（BSP 的 0 只是 -44dB，還聽得見，所以 0 走的是靜音而
不是最小音量）。音量不寫進卡片，每次開機回到預設的 60。

實測（MOVIE10，60 秒、跑三輪）：

| | 無音訊 | 有音訊 |
|---|---|---|
| 每格讀檔 | 2.18 ms | 4.32 ms |
| 每格解碼 | 2.90 ms | 3.72 ms |
| 每格轉色 | 12.28 ms | 12.29 ms |
| 每格合計 | 17.37 ms | 20.33 ms |

讀檔變兩倍（卡片要同時餵影格與音訊），但 24fps 的預算是 41.7ms，
餘裕還很大：**1401~1403 格 = 23.4fps、欠載 0、讀取錯誤 0、解碼失敗 0**。
補資料只佔 6.1%（686 次、平均 5.37ms）。

**音畫同步沒有另外做，而且量過之後確定不必做。** 整部播到 9 分 17 秒：
影片 13,370 格 ÷ 24fps = 557.08 秒、音訊 557.14 秒，**差 58 毫秒（0.010%）**，
欠載 0、讀取失敗 0、解碼失敗 0，格率 23.99fps。

因為兩邊的時基同源：影格節奏走 `HAL_GetTick()`（SysTick <- PLL1 <- HSI），
音訊取樣率走 I2S 位元時脈（<- PLL3Q <- **同一顆 HSI**）。同源就不會漂。

### 接續上次的位置

按「返回」離開影片時會記住播到第幾格，下次進去接著播（聲音也會跳到同一點）。
**每部影片各記各的** —— 看到一半跳去看別部再回來是很自然的用法。

三個邊界：

- **快看完了就從頭播**（剩不到十秒）。不然「接續」等於一進去就結束，
  最後那幾秒會變成一個進不去的狀態。
- **重新掃卡就忘記**。影片的順序可能跟上次不一樣，寧可從頭播也不要
  接到別部影片的位置。
- **不寫卡片，重開機就忘記**。使用者要的就是這樣，而且完全不碰卡片 = 零風險。

位置記在離開播放的那**一個**出口，不是在每個 break 前面各記一次 ——
漏掉一個就會變成「有時候記得有時候忘記」（board-notes 14.5 那一類）。

### DTCM 黑盒子（`0x20004020` 起）

`mode=HOTPLUG` 在這塊板子上目前**完全連不上**（`Unable to get core ID`），
只有 `mode=UR` 連得上 —— 而它會重置，全域變數在 .bss 一開機就被清光。
所以把關鍵狀態放進 DTCM：重置洗不掉，啟動碼也不會清它。

```bash
STM32_Programmer_CLI -c port=SWD mode=UR -r32 0x20004020 64
```

| 位移 | 內容 |
|---|---|
| `[1]` | 開機次數（一直跳 = 重置迴圈）|
| `[2] [3]` | **上一輪**最後到達的階段與 `uwTick`（掛在哪裡看這個）|
| `[4]` | `RCC->RSR`：分得出看門狗／軟體重置／按 reset |
| `[8] [11]` | 掃卡次數、掃到幾張（重複掃卡 = 螢幕看起來卡在「載入中」）|
| `[14] [15]` | `present()` 等不到垂直消隱重載的次數 / 總次數 |

`[14]` 是分辨「相簿掛住」與「畫面停在最後一幀」的關鍵 —— 這兩件事在螢幕上
長得一模一樣。

### 寫入上限是卡片的問題（已結案）

`g_dbg_wrtest` 在原本那張 8GB 卡上量到：**每次重新初始化之後只能寫 15 次，
第 16 次必定失敗，之後永遠失敗**。降時脈（CLKDIV 4→8）、散開到 30 個不同
磁區，都還是精準 15。

換一張卡，**同一塊板子、同一份韌體、同一段程式碼**：

| 卡片 | 成功 | 失敗 | 錯誤 |
|---|---|---|---|
| 8GB FAT32 | **15** | 85 | DPSMACT 卡住、BSP -4 |
| **512GB exFAT** | **100** | **0** | 全部 0 |

最愛的完整功能測試在健康的卡上也是滿分：收藏 20 張、20 張全部對上、
20 張全部播出來、0 失敗，每張剛好 2 次寫入。

**所以是那張 8GB 的卡。** 主機端可以連續小型寫入 100 次零錯誤。

「可是那張卡在電腦上寫就沒事」—— 電腦用的是 USB 讀卡機，**那是另一個主機**，
時序、協定實作、供電都不同。邊界問題本來就是「組合」的性質。這跟第十章
那顆 PSRAM 是同一種東西：同一顆晶片、同一份韌體，一塊板子好一塊板子壞。

完整的推論過程（包含我把結論翻過去又翻回來）在 board-notes 20.12 / 20.13。

## 影像管線

```
SD 讀檔 → 硬體 JPEG 解碼 → YCbCr 轉 RGB888
        → 面積平均縮放（線性光空間）→ 非銳化遮罩 → 有序抖動轉 RGB565 → 旋轉

（銳化預設關閉，見下。）
```

每一步的理由寫在 `app_src/photo.c` 的檔頭。重點：

- **解碼成 RGB888 而不是面板原生的 RGB565**。一開始就砍成 5/6/5，後面所有
  處理都在被量化過的資料上做，誤差會累積。
- **面積平均而不是最近鄰**。1200×1800 縮到 480×800 是 2.25 倍，最近鄰等於
  每 5 個像素丟掉 4 個。
- **盒子邊界要用分數覆蓋率**。整數邊界（來源像素非全進即全出）在 2.25 倍時
  盒子大小會以 2,2,2,3 的週期跳動，邊緣每四個目的像素錯開一次 —— 規律的
  階梯正是「鋸齒」的來源。
- **平均要在線性光空間做**。加權平均只在線性光才有物理意義；sRGB 是感知編碼，
  直接對編碼值平均的誤差集中在邊緣。**這兩件事是相乘的**：單獨做任一項只改善
  一成多，兩項一起改善六成五。
- **銳化預設關掉**（`SHARPEN_AMOUNT 0`）。縮小確實會讓影像變軟，補銳化是
  合理的直覺，但它同時把邊緣過渡壓得更陡 —— 2.25 倍縮小後過渡只剩一兩個
  像素寬，壓陡的代價就是過衝亮暈與階梯感。用真實照片放大八倍並排比較後，
  銳化是**唯一**看得出差別的變數（換濾波核肉眼分不出來），所以關掉。
  想要銳一點改這個數字即可，60 以上邊緣會出現可見亮暈。
- **最後才量化並加抖動**。RGB565 的紅藍只有 32 階，平滑漸層會有色帶。
- **旋轉折進最後一次寫入**。面板 800×480 橫式；直立模式把畫布轉 90 度貼上去，
  橫向模式直接對應。兩者只差寫入的基底與步進，內層迴圈不必判斷方向。

### 效能

**2026-08-23 重新實測**（78 張、累計 158.5 Mpx、平均 2.03 Mpx/張）：

`每張 ≈ 639 ms × 來源百萬像素 + 345 ms`（常數項做的是目的地，不隨來源尺寸變）

| 階段 | 每張 | 佔比 |
|---|---|---|
| 讀檔（SD） | 87 ms | 5% |
| JPEG 解碼（**輪詢版**） | 293 ms | 18% |
| 縮放（**含轉色 338 ms**） | 884 ms | 54% |
| 抖動＋旋轉 | 345 ms | 21% |
| 合計 | **1643 ms** | |

**分段時間不能相加。** 帶狀串流之後轉色是夾在縮放迴圈裡面的，兩個計時器
刻意分開記帳（好跟改造前的數字比），所以 `scale` 已經包含 `cc`。
不重複計算的話是 87+293+884+345 = 1609 ms，跟 1643 差的約 34 ms 是開檔等
未計時的開銷。

註：這個模型跟帶狀串流**改造前**量的（647 × Mpx + 327）幾乎一樣 ——
不是數字沒更新，是**改造本身只賺了幾個百分點**。board-notes 15.10 早就
量出原因：管線是 CPU 受限不是頻寬受限，砍掉全尺寸 RGB888 中間層省下的
PSRAM 往返，被 write-allocate 的填線讀取抵銷掉大半。

展示時間是 `max(間隔設定, 解碼時間)`，所以**超過約 2.6 Mpx 的照片在間隔設
2 秒時會拖到 2.5 秒左右**。不影響操作，但節奏會不一致；在意的話把間隔調成 3 秒。

`app_src/photo.c` 有一整組 `g_dbg_us_*` / `g_dbg_sum_*` 分段計時（微秒，DWT
週期計數器），以及累計來源像素數。**隨機播放每次抽到的尺寸分布都不同，
比較兩次執行一定要用「每百萬像素幾毫秒」，不能直接比平均毫秒數。**

### 畫質測試台

`test/` 可以在 PC 上跑「解碼之後」的整段管線並輸出 PNG。畫質只能用眼睛判斷，
在板子上改一次要重編、重燒、還得手動操作選單。

```bash
cd test && ./run.sh              # 內建測試圖樣
cd test && ./run.sh photo.jpg    # 另外加上真實照片
python reference.py out          # 產生 PIL 的對照組（含線性光 Lanczos）
python compare.py out rings 120 250 90 70 6 <變體...>   # 並排＋數值差異
```

**它直接編譯 `app_src/photo.c` 本體**，不是重寫一份演算法 —— 重寫的話比較的
就不是板子上實際跑的東西。`run.sh` 的 `VARIANTS` 每組一個編譯旗標，
可以一次比較 `RESAMPLE_LINEAR`、`SHARPEN_AMOUNT` 的各種組合。

**評分基準要小心**：拿某個特定演算法（例如 Lanczos）當基準等於預設它是對的，
那把尺會獎勵銳利度，把「刻意用銳利度換無 ringing」的做法判成更差。
`groundtruth.py` 從解析式圖樣超取樣求出真實答案，與任何演算法無關 ——
任何「A 比 B 好」的結論，先確認基準不是 A 或 B 的近親。
細節在 [docs/board-notes.md](../../docs/board-notes.md) 第十五章。

## 這塊板子的兩個硬體問題

**PSRAM 撐不住 BSP 預設的 200MHz**。時序餘裕有板子個體差異，這塊落在錯誤側，
會偶發單一位元讀取錯誤 —— framebuffer、播放清單、解碼緩衝區全在 PSRAM 裡，
症狀是畫面閃爍、照片路徑字串莫名其妙壞掉（`FR_NO_PATH`）。

`shared/xspi_psram.c` 覆寫 BSP 的 `__weak MX_XSPI_RAM_Init()` 把時脈減半成
100MHz。實測掃描 16MB：200MHz 有一百多萬個字出錯、0 個乾淨區塊；100MHz 是
零錯誤、256/256 全乾淨。**沒有效能代價**，LTDC 只需要約 46 MB/s。

**外部 NOR Flash 有兩個固定壞格**：`0x70170466` 與 `0x700217C6`，
**壞的都是 bit 2**（比較像某條位元線在特定區塊偏弱，不是隨機耗損）。
每次燒錄都會出現，目前兩個
落在 FatFs 的查表資料裡，無害。`scripts/flash.sh` 改成整份讀回自己比對，並用
`nm -S` 指出不符的位元組落在哪個符號 —— 落在查表資料可以忽略，落在 `.text`
的函式就不行。不要只看 `STM32_Programmer_CLI -v`，它只丟一行就中止，
判斷不了嚴重性，而且偶爾會誤報。

## 幾個踩過的坑

**FatFs 預設值不能直接用**（`tools/patch_project.py` 會改）：
- `FF_USE_LFN=0` → 長檔名關閉，`IMG_20240101_120000.jpg` 會變 `IMG_20~1.JPG`
- `FF_CODE_PAGE=932`（日文）→ 要改 950（繁中）
- `FF_FS_LOCK=2` → 同時只能開 2 個檔案或目錄，遞迴掃到第三層再開檔就會拿到
  `FR_TOO_MANY_OPEN_FILES(18)`

**不使用 ST 的 `fatfs.c`**。它的 `MX_FATFS_Process()` 含 `f_mkfs`（格式化）
與寫測試檔的路徑。掛載那幾行自己寫，把誤格式化的可能性從根本移除
（而且 `FF_USE_MKFS` 預設就是 0，`f_mkfs` 根本沒編進韌體）。磁碟介面在
`core/sd_bsp_diskio.c`，預設回報 `STA_PROTECT` —— 只有收藏會短暫解開，
見上方「寫入安全」。

**`HAL_JPEG_Decode()` 返回後讀不到輸出長度**。HAL 在結束時會先用
`DataReadyCallback` 把長度交出來，然後把 `JpegOutCount` 清成 0。`__weak` 的
預設回呼什麼都不做，長度就這樣掉了，轉色函式收到 `DataCount=0` 一個 MCU 都
不會轉，整片緩衝區是雜訊。必須自己實作回呼把長度接住。

**`jpeg_utils` 的 `JPEG_RED_OFFSET` 是位元位移，不是位元組索引**。RGB888 預設
`RED_OFFSET=16`，記憶體順序是 B,G,R。設 `JPEG_SWAP_RB=1` 才是直覺的 R,G,B。

**`BSP_SD_Init()` 可能永遠不返回**。HAL 的 `SD_InitCard()` 裡有
`while (sd_rca == 0U)`，沒有逾時保護。卡片若停在異常狀態不回應 CMD3 就出不來
（實測畫面停在「載入中」，CPU 正常在跑、故障暫存器全 0，就是空轉）。程式自己
跳不出無窮迴圈，只能靠獨立看門狗（16 秒）兜底；重置後讀 `RCC_FLAG_IWDGRST`
判斷是被看門狗打掉的，先擋住不要再碰卡片，並提示使用者拔卡重插。

軟體重置**不會**切斷 SD 卡電源，所以在讀取途中重置板子容易把卡片留在異常
狀態。除錯時要注意。

**`ChromaSubsampling = 0` 是 4:4:4，不是 4:2:0**。緩衝區照 4:2:0 配的話，
4:4:4 的照片（每像素 3 bytes，兩倍空間）裝不下，而 HAL 在輸出緩衝區滿時
**繞回開頭續寫** —— 症狀正是「照片底部跑到最上面、底部殘留舊資料」。
輸出緩衝區要照 4:4:4 最壞情況配，容量檢查照實際取樣格式算。

**`DataReadyCallback` 裡不要呼叫 `HAL_JPEG_ConfigOutputBuffer`**。解碼結束
時 HAL 也會呼叫回呼，這時再餵新緩衝區會反覆觸發，把整塊緩衝區吃光 ——
輸出長度「精確等於緩衝區容量」就是這個訊號。回呼只記錄長度（取結束位移
的最大值，不要累加）。

**縮放目的地尺寸不要用比例反算**。定點數兩次截斷會讓 800 變 799，最後
一列永遠沒畫到。填滿模式的目的地直接寫死成整個螢幕，讓誤差落在來源取樣
座標上。

**`BSP_LCD_DisplayOn` 不會開背光**（`DisplayOff` 會順手關掉），要自己把
GPIOG15 拉高。**`BSP_SD_IsDetected` 只讀不設定偵測腳**，第一次
`BSP_SD_Init` 之前要自己把 `SD_DETECT_PIN` 設成輸入，否則讀到浮接電位。

**觸控座標要在確認的當下抓**。確認完再讀一次，輕點時手指已放開會撲空，
按鈕就像沒反應。等待放開要連續數次都讀不到才算（放開瞬間會彈跳）。

**同一次觸碰會被兩個迴圈各吃一次**。暫停迴圈判到「繼續」而恢復播放，
播放迴圈的「點畫面暫停」又把同一次觸碰算進去，於是立刻彈回暫停 ——
症狀是「按繼續沒用」，而實體鍵可以，因為它是閂鎖旗標不會被讀兩次。
切換到另一個也在讀同一個輸入的狀態之前，必須先把該事件消費掉。

**只被讀、從來沒被寫的狀態變數等於常數**。`g_scroll` 就是這樣 ——
繪製與命中判定都用了它，但沒有任何一行寫入，所以第六個以後的資料夾看不到
也選不到，而畫面上還寫著「上下滑動看更多」。`grep` 變數時要分清讀與寫。

**「反應慢」通常是好幾個延遲疊在一起**。實測拆開來是輪詢間隔 30ms ＋
「動作等手指離開」220ms ＋ 暫停圖示 1000ms ＋ 重複的等待放開 220ms，
合計約 840ms。單獨看每一項都還好。

**疊加層畫在顯示中的那塊 buffer，存還原必須成對**，而且要收斂到一對函式裡；
漏掉一次控制列就永久烙在那塊 buffer 上。搬移方向要看畫布方向 ——
直立時邏輯 x 是實體列。

**疊加層不要跟著照片轉**。AUTO 模式逐張決定畫布方向，但使用者的手一直在
同一個地方。而且 `read_touch()` 回傳的永遠是直立座標，跟著轉的話判定會錯。

**固定寬度的紀錄不能拿補齊字元當結束符**。最愛清單每筆補空白到固定長度，
而我拿空白當終止字元 —— 使用者的資料夾叫 `Ayu Makihara (...) 77 set in 1`，
路徑一有空白就被截斷，比對永遠失敗（收藏當下愛心變紅，下次看到又是空心）。
要從固定的結尾往回剝掉補的空白。**而且我先前的測試照片全在沒有空白的
資料夾底下，所以完全測不到** —— 挑測試資料要刻意挑最醜的：有空白、有中文、
有括號、路徑最深、檔案最大的那幾張。

**加了一個保護之後要問「所有的失敗路徑都經過它嗎」**。餵看門狗的呼叫先前
只放在「等待卡片」的迴圈裡，但讀取一失敗就直接 return、根本走不到那裡；
累積起來一樣會超過 16 秒。漏掉的是「立刻失敗但重複很多次」那條。

更完整的版本（含 LTDC、DMA2D、PSRAM、建置系統）在
[docs/board-notes.md](../../docs/board-notes.md)。

```
  reference.py     PIL 對照組（sRGB / 線性光 × BOX / 三角 / 三次 / Lanczos）
  groundtruth.py   解析式圖樣的超取樣真值，不依賴任何演算法
  ssim_downscale.py  Öztireli & Gross 2015 的 SSIM 最佳化縮小（研究級對照）
  compare.py       並排圖＋平均絕對差
  fb2png.py        framebuffer 轉直式 PNG
  zoom.py          裁切放大到像素等級
scripts/     setup / build / flash
tools/       genfont.py（字型產生）、patch_project.py（改 CubeIDE 專案檔）
```

共用程式在 repo 根目錄的 `shared/`：`gfx.c`（繪圖層，沿用 tetris 專案；
方向可在執行期切換，預設直立所以 tetris 行為不變）、
`xspi_psram.c`（PSRAM 降頻，板子個體差異的補償）。`scripts/build.sh` 會把

## 照片放不出來？先用 checkpic 檢查

硬體 JPEG 解碼器**只吃 baseline JPEG**。progressive JPEG 副檔名一樣是
`.jpg`、電腦上也打得開，但板子解不開 —— 而症狀是**畫面看起來像卡住**
（相簿在幾十毫秒內一張張失敗，螢幕上沒有東西可換），完全看不出原因。

2026-08-24 使用者丟了一個資料夾進去，66 張裡有 64 張是 progressive。

```bash
python tools/checkpic.py 資料夾        # 只檢查
python tools/checkpic.py --fix 資料夾  # 順便轉成 baseline（原地覆蓋）
```

會一併檢查其他限制：**檔案 2MB 上限**、寬度 3413、像素總量、CMYK。

**相簿現在會自己擋下來並在螢幕上說話**：不是 baseline 的圖在送進硬體解碼器
之前就被 SOF 檢查攔掉（20016 ms -> 11 ms），連續全部失敗會提示並回選單，
只有一兩張壞掉則提示兩秒但不打斷播放。細節見 board-notes 22.8 / 22.9。

`--fix` 修得動三種：progressive、檔案過大、尺寸過大。**過大的會先縮小再壓** ——
面板只有 800x480，一張 12MP 的手機照片用不到那些細節（實測 4000x3000 的
9.8MB 圖縮到 1.26MB 就過關）。不是 JPEG 與 CMYK 修不動，會列出來讓你自己處理。
使用者桌面的 `影像轉檔工具\` 有一份複本與拖放用的 `.bat`。
