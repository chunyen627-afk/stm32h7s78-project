# STM32H7S78-DK MJPEG 影片播放（進行中）

**狀態：骨架未完成，建置系統還沒通。** 韌體程式碼（`app_src/video_main.c`）
與影格工具鏈（`tools/packframes.py`）已完成，`scripts/` 的專案產生流程還在修。

## 為什麼有這個專案

相簿那邊留下一個未解問題：JPEG 硬體用 DMA 解碼在**隔離測試裡完全正確**
（輸出與輪詢逐位元組相同、連續 40 次穩定、快 4.8 倍），但整合進相簿的正式
路徑就會在第一張之後把週邊卡死，連 `HAL_JPEG_Abort()` 都救不回來
（docs/board-notes.md 16.6）。唯一的差別是「兩次解碼之間夾了什麼」。

影片是那個問題的極端版本：每秒連續解二十幾次，中間夾著轉色與換頁。
在乾淨的環境裡處理，比在相簿裡邊改邊壞好。

## 目標與已知數字

20 fps = 每格 50 ms。已量到的（board-notes 16.1）：

| 階段 | 800x480 | 佔預算 |
|---|---|---|
| JPEG 解碼（DMA） | 11.4 ms | 23% |
| 轉色 | 待測 | — |
| 換頁 | ~0（寫一個 CFBAR） | — |

解碼有很大餘裕，所以 20 fps 應該可達 —— 但**這是推算不是實測**，
這個專案的第一個任務就是把真實格率量出來。

## 設計

- **沒有 SD 卡**：影格打包成二進位燒進外部 Flash 的空白區（0x71000000）。
  外部 Flash 是記憶體映射的，韌體直接就地讀，不必複製也不必解析容器。
  app 只用 1.5MB，128MB 綽綽有餘。
- **沒有縮放**：影格預先轉成 800x480，轉色直接寫進 framebuffer。
- **沒有 UI**：不引入繪圖層與中文字型。
- **RGB565 輸出**：相簿要 RGB888 是因為後面還要縮放與後製；影片的轉色結果
  就是最終畫面，直接輸出 565 少一個緩衝區與一趟 PSRAM 來回。

## 影格準備

```bash
# 從照片做出有平移縮放的素材（也可以換成真實影片）
ffmpeg -framerate 1 -i src/%03d.jpg \
  -vf "scale=1600:-1,zoompan=...:s=800x480,fps=24" -q:v 5 frames/f%03d.jpg

python tools/packframes.py frames frames.bin   # 120 幀 6.46MB
```
